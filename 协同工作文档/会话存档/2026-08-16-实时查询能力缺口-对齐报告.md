## 一、问题现象

真机语音说「帮我查一下东莞的天气」，系统走慢路径后返回的是**编造的天气**，而非真实天气数据；追问「哪天的」后也无法给出真实结果。

## 二、技术真相（两个认知纠正）

### 1. DeepSeek 裸模型没有搜索能力
- 轻量通道接的是 DeepSeek **裸模型**（`deepseek-chat` API），它基于训练数据（知识截止到某时间点）回答，**不联网、不查实时数据**。
- 「web search 权限」不是模型 API 自带的能力（DeepSeek 官方 App 的联网搜索是 App 层功能，API 拿不到）。
- 所以轻量通道问「今天东莞天气」只能凭记忆**编造**。

### 2. Hermes 装了搜索 skill，但 API 调用时工具未触发
- Hermes 侧已装 `anysearch` 等搜索技能（`~/.hermes/skills/anysearch`）。
- 但 voice-bridge 通过 Hermes API Server（8780）调用时，**工具调用链路未生效**，日志实锤 `tool_seen=false`。

## 三、日志证据（2026-08-16 21:58~22:00，vb-v10.log）

| 语音 | route | tool_seen | llm_ttft | 结果 |
|---|---|---|---|---|
| 帮我查一下今天东莞的天气 | hermes | **false** | 8796ms | 编造 |
| 帮我查一下今天广州的天气 | hermes | **false** | 28099ms | 编造 |
| 深圳的呢（指代追问） | lightweight | false | 562ms | 轻量通道编造 |

关键字段：`route=hermes`（走慢路径）但 `tool_seen=false`（**从未调用任何工具**），慢路径只用了 agent 的「大脑」直接回答，等于用模型知识编造。

## 四、根因

1. **`skill_keywords` 为空**：`voice-bridge/config.yaml` 里 `router.skill_keywords: []`，技能触发词清单从未从 Hermes 已装 skills 抽取（关联 ISSUE-0003）。
2. **Hermes API Server 的 tool-calling 链路未打通**：voice-bridge 通过 `/v1/chat/completions` 调 Hermes 时，Hermes 未走「工具调用」流程，直接当聊天回答。
3. **轻量通道天然无搜索**：DeepSeek 裸模型，实时数据类问题（天气/快递/新闻）必编造。

关联 issue：
- `ISSUE-0001`（长期 RAG 慢路径行为级回归）——「关联遗留」已注明：严格意义的技能触发依赖 `skill_keywords` 配置（当前空）。
- `ISSUE-0003`（技能触发词清单抽取与技能触发验证）——本报告正是该 issue 的深化。

## 五、方案选项（待 Hermes 选型）

### 方案 A：打通 Hermes 工具调用（职责在 Hermes 侧）
- 让 Hermes API Server 在「查天气/查快递」类请求时真正调用 `anysearch` 等 skill。
- 需要 Hermes 侧配置 tool-calling（API Server 是否透传工具定义、agent 是否启用工具循环）。
- 优点：复用 Hermes 已有 skills，能力完整。缺点：Hermes 侧工作量 + 慢路径仍 ~20s。

### 方案 B：voice-bridge 直连数据源（职责在 WorkBuddy 侧）
- 对「天气/快递」等高频实时查询，voice-bridge 命中关键词后直连专用 API（如天气 API / 搜索服务），不走模型编造。
- 优点：快、可控、不依赖 Hermes。缺点：引入新依赖（天气 API key）、需定数据源范围。

### 方案 C：诚实兜底（最快止血，职责在 WorkBuddy 侧）
- 模型/系统对实时数据类问题答不上时，直接说「我暂时查不了实时天气/快递」，而非编造。
- 优点：立即消除「乱说话」，成本最低。缺点：不解决问题，只避免误导。

> 建议：**A（真能力）+ C（兜底）组合**——打通 Hermes 工具调用是正解，但周期长；期间先用 C 兜底避免编造。B 视数据源可行性评估。
