- **结论**：**WorkBuddy 的「纯聊天透传」判断是误判**——Hermes API Server 跑的是真 agent（带工具循环），但 tool_seen 的检测方式错了。

---

## 一、Hermes API Server 真相

Hermes API Server 有三个 agent 端点，**都创建 AIAgent 并跑工具循环**（不是纯 LLM 透传）：

| 端点 | 工具循环 | 工具调用可见性 |
|---|---|---|
| `/v1/chat/completions` | ✅ 跑 agent 工具循环 | ❌ 响应体不返回 `tool_calls`（工具在服务端跑）；工具开始通过 **`event: hermes.tool.progress`** SSE 事件暴露 |
| `/v1/responses` | ✅ 跑 agent 工具循环 | ✅ 返回 spec-native `function_call` / `function_call_output` items |
| `/v1/runs` | ✅ 跑 agent 工具循环 | ✅ 订阅进度事件 |

依据：官方文档 API Server 页 + GitHub issue #9684（「/v1/chat/completions … lose access to tool-call visibility」——chat completions 会丢工具调用可见性，但 agent 循环确实在跑）。

---

## 二、回答 WorkBuddy 三个问题

1. **是否提供真正的 agent 接口（带 tool-calling loop）？** —— 有。三个端点都跑 agent 工具循环。
2. **`model=hermes-agent` 映射的是纯 LLM 还是 agent？** —— **AIAgent（真 agent）**，不是纯 LLM。
3. **是否需要扩展 API Server？** —— 不需要。问题出在 **tool_seen 检测方式**：chat completions 的响应体 `tool_calls` 字段天然为空（工具在服务端跑，不外露），这不是「没调工具」。

---

## 三、WorkBuddy 下一步（改检测方式 + 查编造根因）

1. **改 tool_seen 检测**（二选一）：
   - 继续用 `/v1/chat/completions`：在流式响应里监听 **`event: hermes.tool.progress`** 事件，出现即 tool_seen=true。
   - 或改用 `/v1/responses`：拿 `function_call` / `function_call_output` items，结构化判断工具是否调用。

2. **查「编造天气」真实根因**（这是关键，别停在「接口不支持」）：
   - 改检测方式后，若 hermes.tool.progress 有事件但结果仍编造 → web_search 调了但结果没被模型采纳（提示词/工具结果处理问题）。
   - 若 hermes.tool.progress 无事件 → 模型（deepseek-v4-pro）在 api_server 工具集下没调 web_search，需查 **web 工具集是否真含 web_search 工具实例**（A4 裁剪 `platform_toolsets.api_server=[memory, skills, session_search, web]` 里的 web 是否正确加载了搜索工具）。

## 四、对 voice-bridge 集成的影响

若确认「chat completions 跑 agent 但结果编造」，根因在「web 工具集加载 / 模型 tool-calling 意愿」，需在 Hermes 侧查证修复；voice-bridge 侧只需把 tool_seen 检测改为 `hermes.tool.progress` 事件，安抚语触发条件（route=hermes 已定）不受影响。
