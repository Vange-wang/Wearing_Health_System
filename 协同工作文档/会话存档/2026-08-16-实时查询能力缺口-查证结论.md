## 二、A 根因查证（实测证据）

对 Hermes API Server（`http://127.0.0.1:8780/v1/chat/completions`，model=`hermes-agent`）做两组实测：

### 实测 1：不带 tools 参数

提问「帮我查一下今天东莞的天气」，响应：

```
content: 东莞今天(8月16日周日):雷阵雨转中雨，气温26~34℃...
tool_calls: None
finish_reason: stop
```

→ **直接编造天气，无工具调用。**

### 实测 2：带 tools 参数（OpenAI 标准 function 定义 web_search）

提问同上，附加 `tools=[web_search]`，响应：

```
content: 今天(8月16日)东莞：多云转中雨...26~34℃...
tool_calls: []（空）
finish_reason: stop
```

→ **仍编造天气，tool_calls 为空，tools 参数被忽略。**

## 三、根因判定

1. **候选方向 1（tool-calling 未透传）确认为主因**，但更精确的表述是：voice-bridge 调的 `/v1/chat/completions` 是 **OpenAI 兼容的纯聊天透传**，它不做 Hermes agent 的「工具循环」（tool-calling loop），所以：
   - 不传 tools → 编造；
   - 传 tools → 仍编造（接口不执行工具调用，只是透传给底层 LLM）。
2. **候选方向 2（工具集未加载）**：`platform_toolsets.api_server = [memory, skills, session_search, web]` 配置上已含 `web`，但该配置只在 agent 工具循环里生效，纯聊天接口用不到。
3. **候选方向 3（模型不愿调工具）**：次要，因为即使模型想调，纯聊天接口也没有执行工具循环的通道。

## 六、修正（22:50，据 Hermes 查证回复 + 复测）

**原结论「纯聊天透传」是误判**，更正如下：

1. **Hermes API Server 是真 agent，跑工具循环**。`/v1/chat/completions` 的响应体 `tool_calls` 字段天然为空（工具在服务端跑、不外露），工具调用通过 SSE 的 **`event: hermes.tool.progress`** 事件暴露。之前用 OpenAI SDK 的 `delta.tool_calls` 检测，抓不到这个非标准事件 → 误判 tool_seen=false。

2. **复测证实 Hermes 真的联网查了天气**：流式响应里 `hermes.tool.progress` 事件出现 `web_search`（label「东莞今天天气 实时」）+ `skill_view`（anysearch），工具完成后模型基于搜索结果回答（含当日雷雨大风黄色预警等真实数据），**非编造**。

3. **已修复检测**：`HermesLLM.stream_chat` 改用 httpx 直读 SSE，监听 `hermes.tool.progress` 判 tool_seen。实测「帮我查东莞天气」`tool_seen=true` + `comfort_sent=true` + `tool_ms=10141ms`。

4. **「编造」真凶另有所在**：多轮指代追问（如「深圳的呢」）不命中 tool_keywords → 走**轻量通道 DeepSeek 裸模型**（无搜索能力）→ 编造。这与 Hermes 无关。

5. **下一步**：会话级路由记忆——上轮为查询类（慢路径）时，本轮指代追问也应延续慢路径，避免跌回轻量通道编造。
