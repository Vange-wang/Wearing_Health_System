## 一、慢路径延迟根因（非模型，是 streaming 关闭）

### 实测证据

对 Hermes API Server 发最简单的问题「你好」（不触发工具），时间线：

| 时间点 | 事件 |
|---|---|
| 0ms | 请求发出 |
| 284ms | 首个 SSE 到达（agent 秒回，无冷启动） |
| **18.3s** | 首个 content 出现 |
| 18.3~18.4s | 8 个字 **一次性涌出**（3ms 内吐完，非流式） |

「查深圳天气」同理：18.4s 静默后才出首个工具事件（web_search），工具本身仅 2s + 3.4s。

### 结论

**慢路径 18s 的根因是 Hermes `streaming.enabled=false`（非流式）**——模型要生成完整答案（或完整首段）才发出来，voice-bridge 以为在流式接收，实际是「等 18s 一次收完整」。

**不是 deepseek-v4-pro vs flash 的问题**——Hermes `model.default = deepseek-v4-flash`，压根没在用 pro。但即便 flash，非流式下「你好」首 token 也 18s。

### 待 Hermes 侧行动

1. **开启 streaming**：`streaming.enabled: true`，让 API Server 真流式，首 token 应能降一个量级（这是最大收益、最小改动）。
2. **查证 deepseek-v4-flash 映射**：确认它在 Hermes 里不是映射到「思考型/reasoner」模型（flash 正常首 token 应 ~1s，18s 偏慢，除 streaming 外可能还有 reasoning 开销）。

## 二、「换 flash」结论

Vange 要求「全部换 flash」。查证结果：

- **Hermes 侧**：`model.default` 已是 `deepseek-v4-flash`，无需改。

结论：**模型层已是 flash/chat 级，无需变更**；慢路径 18s 是 streaming 问题（见上），不是模型问题。

## 三、SSML 情感风格不可行（edge-tts 7.2.8 移除）

### 实测证据

按《情感调优-第二轮-SSML风格》实现 `mstts:express-as style="chat"`，合成「你好」结果 **39 秒**（正常 2 秒）。定位：

- edge-tts 7.2.8 官方 PyPI 明确说明：**「Custom SSML support was removed because Microsoft prevents the use of any SSML that could not be generated by Microsoft Edge itself」**。
- `Communicate` 内部对 `<`、`>`、`&` 做 `escape()`，把 SSML 标签转义成纯文本，edge 服务端把标签当正文念出来。

### 结论

`express-as` 情感风格在 edge-tts 7.2.8 里**技术上不可行**，已回滚（恢复纯文本合成）。

第一轮（人设提示词 + 语速 -5%）仍有效。情感化治本只剩**换引擎**（CosyVoice / 火山口语化音色 / GPT-SoVITS 克隆），需立项评估。

## 六、复测结论（2026-08-17 凌晨，streaming 已开启后）

### 实测（Hermes 8780 端口，`streaming.enabled: true` 已生效）

**① 「你好」纯对话（连续 3 次）**

| 次数 | 首 token |
|---|---|
| 第 1 次 | 2447ms |
| 第 2 次 | 2366ms |
| 第 3 次 | 2219ms |

**结论：稳定 ~2.2~2.5s，达标（<5s）** ✅ streaming 生效，首 token 从 18~34s 降到 2.5s，且真流式（逐字涌出）。

**② 「查天气」触发 web_search（连续 2 次）**

| 次数 | 首 token | 首工具启动 |
|---|---|---|
| 第 1 次 | 22.8s（冷态，含搜索） | 2.7s |
| 第 2 次 | 10.1s | 3.2s |

**「查天气」~10s 的拆解**（详细时间线）：

| 阶段 | 耗时 |
|---|---|
| agent 首轮推理（决定调 web_search） | ~3.5s |
| web_search 联网搜索（2 个并行） | ~3.4s |
| 工具结果 → 二次 LLM 生成答案 | ~2.8s |
| **合计首 token** | **~9.8s** |

### 关键查证：flash 是否映射到 reasoner？

**没有映射错**。直连 DeepSeek 官方 API（`https://api.deepseek.com`）实测：

| 模型 | reasoning_content 首现 | 正文首 token |
|---|---|---|
| `deepseek-v4-flash` | 855ms（总长 136 字） | **1230ms（1.2s）** |
| `deepseek-v4-pro` | 1526ms（总长 79 字） | 2125ms（2.1s） |

- `deepseek-v4-flash` 本身是**轻推理模型**（响应含 `reasoning_content` 字段），但推理极短（855ms 出完 136 字），直连首 token 仅 1.2s，**不是被错误映射到重型 reasoner**。
- 走 Hermes 8780 时「你好」2.5s = 直连 1.2s + agent 框架 overhead ~1.3s（memory/skills/tool 描述注入），属合理范围。

### 最终结论

1. **纯对话（快/慢路径无工具）**：首 token 2.2~2.5s，**达标** ✅
2. **「查天气」首 token 仍 >5s（~10s）**，但根因**不是模型映射**，而是「联网搜索」的固有成本：agent 首轮推理 3.5s + web_search 3.4s + 二次生成 2.8s。
3. **flash 映射正常**，无需改模型配置。

### 待 Hermes 侧进一步优化（如需「查天气」也压到 5s 内）

「查天气」10s 是「真联网查实时数据」的成本，要再降只能从三处下手：
- **减 agent 首轮推理**：flash 的 3.5s 首轮含 reasoning，可试 `reasoning_effort` 调低；
- **web_search 提速**：换更快搜索后端或限制搜索源数量；
- **首帧解耦**：voice-bridge 慢路径已有安抚语先行，用户不会干等这 10s（体验上已被安抚语覆盖）。
