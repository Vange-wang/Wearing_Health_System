## 一、问题定义

- 指标口径：**open_ms = 松开按键 → 首帧（第一句 TTS 音频帧）**，这是「首响延迟」的准确定义。
- 真机实测（2026-08-16 20:20~20:28，日志 `C:\Users\86166\AppData\Local\Temp\vb-v04.log`）：open_ms 1941~2983ms，**均值 ~2.5s**。
- 目标：open_ms ≤ 2.0s（硬底线），预留余量目标 ~1.8s。

## 二、延迟实测拆解

以「发烧到三十九度怎么办」为例（open_ms 2476ms，route=lightweight）：

| 环节 | 耗时 | 说明 |
|---|---|---|
| DeepSeek 首 token（llm_ttft） | ~660ms | 冷连接实测 1412ms / 热连接 603ms；服务端 2h 无请求后 TLS 连接被回收 |
| 首句 LLM 生成 | ~430ms | 首 token → 首句完整（分句边界） |
| edge 首句合成（tts_first） | ~1280ms | edge 整句 ~1080ms + miniaudio 解码/重采样/裁静音 ~200ms |
| final_decode + 路由 + 分句 + 队列 | ~150ms | 尾静音 flush 55ms + 调度 overhead |
| **合计** | **~2476ms** | 两处大瓶颈：LLM 首句与 TTS 首句**串行**，各自独立耗时 |

关键结构性问题：**LLM 首句（~1.1s）→ TTS 首句（~1.3s）是严格串行**，TTS 必须等完整句子文本才能合成。

## 三、可行性验证（关键实测）

1. **edge 流式首 chunk ≈ 845ms，整句 ≈ 1080ms**（实测「发烧到三十九度怎么办」首 chunk 845ms / 全 22 chunk 1079ms）。说明 edge 延迟大头在「建连 + 服务端合成首段」，而非「整句合成长度」——**流式首帧只能省 ~200~420ms，不是省 1s**。
2. **miniaudio 可分段解码不完整 mp3**（实测累积 1440 字节即解出 240ms PCM）→ 流式首帧无需 ffmpeg，用 miniaudio 分段解码即可实现。
3. **DeepSeek 冷连接 1412ms vs 热连接 603ms** → 连接保温收益明确，可省 ~200~450ms。

## 四、优化方案（组合拳，目标 ≤1.8s）

### 方案 1：DeepSeek 连接保温（低复杂度，省 ~250ms）
- 现状：A7 只在**启动时**预热一次，之后 2h 无请求 → TLS 连接被 DeepSeek 服务端回收，首请求付冷连接 ~1.4s。
- 改：`LightweightLLM` 加**周期心跳**（每 3~5 分钟发一次 `max_tokens=1` 最小请求，后台线程），保持 TLS 连接热。
- 预期 llm_ttft 稳定 **~450~600ms**（热连接水平）。
- 成本：每 5 分钟一次 1-token 请求，开销可忽略。

### 方案 2：edge 流式首帧（中复杂度，省 ~350~420ms）
- 现状：`EdgeTTS.synthesize` 收集**整句 mp3** → miniaudio 整段解码 → 裁静音 → 包 WAV，才发首帧。
- 改：`stream()` 收到**首个 audio chunk** 即用 miniaudio **分段解码**发首帧；后续 chunk 增量解码、增量发帧（首段 100ms、后续段 300ms）。
- 预期 tts_first **1280→~860ms**（首 chunk 845ms + 分段解码 ~15ms）。
- 固件**无需改动**（`read_exact` 已支持多帧连续播放）。

### 方案 3：提示音先行（首帧解耦，核心，Vange 拍板）
- 现状：首响 =「LLM 首句完整 + 首句 TTS」串行，两段各 ~1s，物理上难压到 2s 内。
- 改：**启动时预合成 6 个口语化应声词**（好嘞 / 来啦 / 好的呢 / 嗯嗯 / 稍等哦 / 明白，随机轮换、避免连续重复）缓存内存；**LLM 首 token 到达即发提示音作为首帧**，答案随后。
- 预期 open_ms ≈ llm_ttft ≈ **~1.0s**（提示音预合成，~0ms 合成耗时）。
- 交互变化：先应一声（有感情、不单调），再听答案——同 Siri/小爱。

### 最终实测结果（2026-08-16，日志 vb-v06.log）
| 指标 | 优化前 | 优化后 |
|---|---|---|
| open_ms（首响） | 1941~2983ms（~2.5s） | **999~1102ms（~1.06s）** |
| tts_first（edge 首句） | ~1350ms | ~1000ms（流式首帧） |
| 达标情况 | 0/5 ≤2s | **5/5 ≤2s（余量 ~100%）** |

> 三件套：①心跳保温（llm_ttft 稳定）②流式首帧（长回复更顺）③提示音先行（核心，open_ms 2.5s→1.0s）。

## 五、工程改动点与风险

| 改动 | 文件 | 风险 |
|---|---|---|
| 周期心跳保温 | `app/llm.py`（LightweightLLM） | 低：需处理线程退出、服务关闭时停心跳 |
| 流式首帧（分段解码 + 增量产帧） | `app/tts.py`（EdgeTTS）+ `app/pipeline.py` | 中：①mp3 首段有编码 priming，首帧可能含短静音，需实测调「累积阈值」②**sentence_gap_ms 当前按「每帧」加 300ms 停顿，一句话拆多帧后需改为「仅句间」加停顿**，否则句内断续 |
| 测试 | 新增/扩展延迟用例 | 需打点验证 open_ms ≤ 2s |
