# 低功耗休眠与按键唤醒 — 方案对齐

- **提出方**：Vange（2026-08-17）
- **整理**：WorkBuddy
- **状态**：待 Hermes 起草 Spec / 对齐

---

## 一、需求

1. 设备**空闲一段时间（3 分钟）无互动**后，自动进入**浅睡（Light Sleep）**省电。
2. **按键呼叫**（顶部圆键 / Boot 键）即从浅睡中醒来，恢复语音交互。
3. **未来扩展**：唤醒词自动呼叫（此期不做，但方案要为其留余地）。
4. 目标：为将来**电池供电**（ISSUE-0005）做功耗储备。

Vange 拍板的三项决策：
- 休眠深度：**浅睡 Light Sleep**（唤醒快，非深睡）
- 空闲时长：**3 分钟**
- 供电场景：为将来电池供电做准备

---

## 二、技术方案

### 2.1 休眠模式选型

| 模式 | 功耗 | 唤醒延迟 | 按键唤醒 | 唤醒词唤醒 |
|---|---|---|---|---|
| Modem sleep（仅关 WiFi） | ~20-30mA | 无 | — | 可 |
| **Light sleep（浅睡，选型）** | **~0.8mA** | 毫秒级 | ✅ | 可 |
| Deep sleep（深睡） | ~10μA | 约 10 秒（重连 WiFi） | ✅ | ❌ 不可 |

选 **Light sleep**：省电可观（相比 modem sleep 降一个量级），唤醒毫秒级，且保留未来加唤醒词的能力。

### 2.2 唤醒源

BOX-3 两个按键均为 RTC GPIO，可作为 Light sleep 的 ext1 唤醒源：

- `BSP_BUTTON_CONFIG_IO = GPIO_NUM_0`（顶部圆键）
- `BSP_BUTTON_MUTE_IO = GPIO_NUM_1`（MUTE 键）

用 `esp_sleep_enable_ext1_wakeup()` 同时挂两个 GPIO，任一按下即唤醒。

### 2.3 空闲计时

- 维护"最后活跃时间戳"，每次语音交互完成（`voice_round()` 返回）刷新。
- 监控逻辑（在 `talk_task` 空闲循环内）：`now - last_active > 3 分钟` → 进入浅睡。

### 2.4 进入浅睡前

1. 停止录音/播放（codec 关闭或挂起）。
2. 断开 WiFi（`esp_wifi_stop()`），避免空耗。
3. 配置 ext1 唤醒源（GPIO0 + GPIO1）。
4. `esp_light_sleep_start()`。

### 2.5 唤醒后恢复

1. 重新 `esp_wifi_start()` + 连接（复用现有 `wifi_connect()` 或轻量重连）。
2. 重新 `mdns_init()`（mDNS 需随 WiFi 重建）。
3. 重新初始化音频 codec（若 light sleep 期间断电）。
4. 防抖：忽略"唤醒瞬间"的按键边沿，避免误触发一次语音。

## 三、关键技术风险 / 待 Hermes 决策点

1. **WiFi 处理方式**：浅睡时完全断开（省电多、唤醒要重连 ~几秒）vs 保留 modem sleep 混合（唤醒快、省电少）。建议**浅睡断开 + 唤醒重连**，因为 3 分钟空闲后本就不需要秒级响应。
2. **音频 codec 是否断电**：ES7210/ES8311 在 light sleep 时是否保持供电？建议断电省电，唤醒后重开（需验证 codec 重开时序）。
3. **唤醒后 mDNS 重建**：light sleep 唤醒后 WiFi 重连，mDNS 需要重新 init（否则 `voicebridge.local` 解析失效）。
4. **空闲判定的语义**：仅"按键空闲"还是"语音交互完成后空闲"？建议按"最后一次语音交互完成"起算 3 分钟。
5. **防抖机制**：唤醒瞬间的按键按下要排除，避免"唤醒 + 立刻开始录音"的误判。

---

## 四、验收标准（建议）

1. 设备空闲 3 分钟无交互 → 自动进入浅睡（功耗显著下降，可测电流）。
2. 按顶部圆键或 MUTE 键 → 毫秒级唤醒，WiFi 重连成功后恢复正常语音交互。
3. 唤醒后 `voicebridge.local` 可正常解析（mDNS 已重建）。
4. 反复"休眠 → 按键唤醒 → 对话 → 再休眠"循环稳定，无内存泄漏/卡死。
