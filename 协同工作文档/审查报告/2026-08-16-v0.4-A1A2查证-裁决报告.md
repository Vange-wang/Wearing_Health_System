## 一、A2 增量 ASR 查证 —— 扎实，方案确认

- SenseVoice 是批式模型，不支持流式（源码级实锤：仅有 `OfflineSenseVoiceModelConfig`，`OnlineRecognizer` 构造方法列表无 SenseVoice）。Spec §9 已预警，查证坐实。
- sherpa-onnx 1.13.5 已内置流式（`OnlineRecognizer` + `from_zipformer2_ctc` 等），**框架零改动**，`asr.py` 只需换 recognizer + 加流式 feed / partial-final 回调。
- 流式模型选型 `streaming-zipformer-bilingual-zh-en`（~240MB，中英双语，Apache-2.0）合理。

**裁决 A2：确认换流式模型（弃 SenseVoice 批式）**，框架零改动。端点检测用「按键松开」（A3），禁用 enable_endpoint_detection。

**配合项**：模型 ~240MB 下载需 hf-mirror 直连或 Clash 代理（GitHub release 被墙）。WorkBuddy 按代理姿势处理（hf-mirror 直连优先，否则 `export ALL_PROXY=127.0.0.1:7800`）；若需开 Clash，Vange 配合。

## 二、A1 opus 参数 —— 关键发现，裁决改 raw PCM

WorkBuddy 实测三方案（opencore / pyogg / opuslib）均失败，结论「Windows 无纯 pip 解裸 opus 方案」成立：

| 方案 | 失败原因 |
|---|---|
| opencore | 依赖 memojito 用 Python2 语法，py3.11 编译挂 |
| pyogg | 仅 OGG 容器解码，无裸 opus 包解码 |
| opuslib | ctypes 需系统 libopus DLL（未捆绑） |

而固件 esp-opus 输出的是**裸 opus 包**（非 OGG 容器），三者都不匹配。

**WorkBuddy 出路推荐（raw PCM）成立**：局域网场景 16k/16bit/mono PCM = 32KB/s，WiFi 局域网带宽可忽略，opus 压缩（32KB→2KB）在此无收益，却换来「服务端解码依赖 + 固件编码」两层成本。

**裁决 A1：opus 改 raw PCM**。理由：
1. v0.4 是局域网（手机热点 2.4G），PCM 32KB/s 可忽略，opus 压缩无收益。
2. 零 opus 依赖（服务端 + 固件都省），最快打通真机链路。
3. Spec 红线「PCM 16k/16bit/mono 进 ASR」本就一致——PCM 直进流式 ASR，无需 opus 解码层。
4. opus 的价值在广域网（远程访问时压缩省上传带宽），登记 future issue（ISSUE-0006），不阻塞 v0.4。
