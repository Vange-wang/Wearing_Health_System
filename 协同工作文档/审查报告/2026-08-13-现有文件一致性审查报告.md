### P1-05 流式响应缺少可靠的应用层分帧

**证据**

- `规划文档/Spec文档/2026-08-11-语音桥-spec-v0.2.md:100-109` 要求每个 HTTP chunk 为一句完整 WAV，整体 `Content-Type: audio/wav`。
- 同一 Spec `:267,313-314` 又把 chunk 可独立播放作为验收，并将 ESP32 解析留到 M1。

**问题**

HTTP transfer chunk 不是稳定的应用消息边界，可能被服务器、代理或客户端拆分、合并。多个 RIFF/WAV 文件串接也不是标准的单一 `audio/wav` 实体。

**建议**

改用以下任一明确协议：长度前缀帧、自定义 multipart boundary、WebSocket 二进制帧，或一个连续 PCM/编码音频流。不得把 HTTP chunk 边界直接当句子边界。

### P1-06 `open_ms` 和首包响应头定义无法同时成立

**证据**

- `规划文档/Spec文档/2026-08-11-语音桥-spec-v0.2.md:107-108` 定义 `open_ms` 为请求开始到首 chunk 首字节的墙钟时间。
- 同一 Spec `:197-204` 又定义为 `asr + llm_ttft + tts_first`。
- 分项求和遗漏 VAD、解析、首 token 到满足分句条件的等待、框架和首字节发送开销。
- `X-Timing-First-Token` 被要求放在响应头中，但这些数据要到第一句生成后才完整。

**影响**

按分项公式可能低报延迟并错误通过 ≤1.5 秒验收；按常规流式响应又无法在发 header 前知道完整数据。

**建议**

唯一权威指标应为 `perf_counter(first_body_send) - perf_counter(request_received)`；分项只用于解释。实现上需预取首句后再构造响应，或使用明确的首帧元数据/响应 trailer 方案。

### P1-08 v0.1 自动化 gate 会假阳性

**证据**

- `voice-bridge/tests/test_smoke.py:120-131` 接受 HTTP 200、400、502，且只有 200 时才检查 `X-Timing`。
- 该用例使用静音并在注释中承认可能到不了 LLM。
- `Code文档/v0.1自测报告.md:40-48` 和第2轮审查报告 `:69-81` 将其描述为全链路 X-Timing 用例通过。

**影响**

无语音或上游失败仍可显示 PASSED，自动化不能证明全链路或 X-Timing。

**边界说明**

三份已保存的真实响应均为 HTTP 200，且响应头中的 `X-Timing` 与报告一致。因此问题是自动化 gate 和审查措辞过度，不代表正常链路没有跑通。

**建议**

把测试拆成：确定性的 mock 全链路 X-Timing 测试，以及明确启用的真实集成测试；真实测试非 200 必须失败，不能接受 400/502。

### P1-09 v0.1 错误码和“每请求日志”未完整实现

**证据**

- `voice-bridge/app/main.py:97-105` 只将 `ValueError` 映射到 400/413，其他 ASR 异常一律 502。
- 损坏但扩展名为 `.wav` 的文件会触发 WAV 解析异常，当前返回 502；Spec `规划文档/Spec文档/2026-08-11-语音桥-spec-v0.1.md:65-74` 要求坏音频/ASR失败为 400。
- Spec `:76` 要求每个请求一条结构化日志；`main.py:77-125` 的失败路径提前返回，唯一 JSON 请求日志位于成功路径 `:130-139`。

**影响**

客户端会把输入问题误判为上游故障，失败请求也无法按 Spec 审计和定位。

**建议**

增加明确的 WAV 解析异常映射；把统一结构化日志放入覆盖成功与失败的请求级 `finally`/中间件，并记录状态、阶段和错误类型，不记录敏感正文。
