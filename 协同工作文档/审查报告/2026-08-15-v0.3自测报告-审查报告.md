## 三、核心问题：延迟未达标（根因 + 裁决建议）

### 根因（已定位，非实现缺陷）

- v0.2 直连 DeepSeek：首 token 0.5~0.75s → open_ms 1.5s
- v0.3 走 Hermes agent：首 token ~3.1s → open_ms 3.5s
- 差值 ~2.4s = Hermes agent 的**启动开销**（记忆检索 + skills 扫描 + 工具集解析注入 system prompt，模型处理大 prompt），**非工具调用导致**（`tool_seen=false`）。

关键判断：**A2（分段计量）与 A4（工具裁剪）都消解不了这个延迟**——它们针对的是「工具调用」开销，而 3.1s 是「agent 本体」开销。WorkBuddy 在报告 §4 也正确指出了这一点。这是「接入 Hermes」的本质代价。

### 裁决建议（分两步，需 Vange 拍板）

**第一步（v0.3 收尾，建议接受）**：放宽纯闲聊 open_ms 验收线到 **稳态 ≤4000ms**（含 agent 固定开销），冷启动剔除。理由：共用记忆目标已达成（v0.3 灵魂），延迟代价是 agent 架构固有成本，语音健康管家场景（功能性查询为主）3.5s 可接受。

**第二步（优化，单独立项，不阻塞 v0.3）**：评估 Hermes「轻量直通」通道——纯闲聊走「跳过记忆/技能/工具预加载的 bare 模型直答」，需要记忆/技能时再走完整 agent。若 Hermes 具备此能力，纯闲聊延迟可回 ~1.5s。此方向为 Hermes 产品层能力，**需先查证 Hermes 是否支持**，参考 OI-004 edge 评估的独立任务模式。

**不推荐**：降级非流式（与 v0.2 成果冲突）。

### 需 Vange 拍板

是否接受 v0.3 的 ~3.5s 开口延迟（产品取舍：延迟 vs 记忆/技能价值）。此为唯一阻塞决策。
