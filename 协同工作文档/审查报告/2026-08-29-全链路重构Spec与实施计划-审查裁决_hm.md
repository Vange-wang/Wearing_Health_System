## 三、6 项强制修正（实施前/中必须处理）

### 修正 1（关键）：首字延迟基线记录时机错误

- **问题**：Task 1（固化变更前证据）只记录服务端测试基线 + 文件哈希，**没有记录首字延迟基线**；首字基线出现在 Task 18 Step 1（"when COM5 present... if current baseline still available"）——那时代码已全改完，"改动前基线"已不存在。
- **要求**：**首字延迟基线必须在 Task 1 用当前未改固件记录**（7 个打点，至少 5 轮），否则首字延迟门（Spec §10）无法对照。这是最高铁律的落地前提。

### 修正 2：Task 8（受控实验）需用户物理配合门

- Spec §13 已声明"真机测试需用户物理交互"，但 Task 8 无显式 gate。E0/E1/E2 需"同一手指/压力 + 外部血氧仪同步"，纯软件无法完成。
- **要求**：Task 8 Step 2-4 前加"等待 Vange 物理配合"检查点，未配合不得标记通过。

### 修正 3：E2 候选与"生产候选"表述需统一

- Spec §6.1 说"生产候选 LED 保持 0x17"但 §6.4 判定规则允许 E1 微动失败后"选择 bd9e564 四重门限 0x17"。两者不矛盾但需明确：**最终生产配置的唯一权威 = E0/E1/E2 判定结果，不得预设**。建议 Spec 6.1 首句改为"生产候选 LED 暂定 0x17，以 §6.4 判定结果为准"。

### 修正 4：Task 7 驱动可靠性"回滚只覆盖算法文件"与"驱动重构"边界需明确

- Spec §2.3 说"回滚只覆盖算法文件，驱动可靠性修复不得同时改变采样参数"。但 Task 7 会改 max30102.c（错误传播/FIFO 溢出）。需明确：**驱动重构（Task 7）与算法受控实验（Task 8）必须串行，驱动改完并验证不改变采样参数后再做 E0/E1/E2**——否则采样参数被驱动改动污染，实验结果无效。

### 修正 5：设备认证的兼容性过渡

- Spec §3.1 说"BOX-3 与服务端必须在同一批次升级"（新增 X-Device-Token）。但 Task 4（服务端认证）与 Task 5（固件认证接线）若不同时部署，会出现**旧固件无 token → 401** 的中断窗口。
- **要求**：明确升级顺序——服务端先加认证但**留白名单/兼容开关**（或先固件后服务端），避免真机运行中断。

### 修正 6：微信 chat_id 已暴露的现有事实

- Spec §5.1 说"微信接收标识的完整值"不得进入源码。但**现有 voice-bridge/config.yaml 已含 wechat_chat_id（P4 时写入）**。修正需确认：该值是否已在 git 历史/当前工作区泄露，迁移时一并处理（Spec §13 已提 Git 历史清理单独授权，需纳入交付物清单）。

## 四、2 项前置核实（建议实施前确认）

1. **D:\esp-box 的 git 状态**：Spec §2.1 说 D:\esp-box 存在"大量用户改动和生成物"，但实施计划 Task 1 只读 status。建议实施前 Hermes 复核 D:\esp-box 工作树，确认哪些是用户改动（不碰）、哪些是可安全修改的工作源码；
2. **"心跳频带能量仅 17-20%"的根因归属**：3adf081 交接把问题归为"信号质量"，但未确认是**光路/接触/模块个体问题**还是**算法问题**。Spec §6.4 判定规则已含"E0 也失败→物理排查"，但建议 E0 实验前先做一次**清洁窗口 + 固定压力**的预检，排除物理因素干扰算法裁决。
