## A. 必须裁决（P1 级，进 v0.2 开发前逐条锁定）

### A1. TTS 主从策略（Vange 2026-08-13 已决，v0.2 Spec 需修订）
- **冲突**：v0.2 Spec §3/§6.3/§8 将 `primary: piper` 设为默认主引擎（OI-004 评估结论）；但 Vange 8-13 已确认 **Edge-TTS 为主引擎、Piper 为故障兜底**。
- **裁决要求**：
  1. `tts.primary` 恢复 `edge`，`fallback` 恢复 `piper`（产品/配置主从不变）
  2. health 分别报告 `configured_primary=edge`、`active_engine=edge|piper`、`fallback_reason`——当前实际落到 piper 只代表 fallback 生效，不代表策略变更
  3. Edge 6.x 403 / Edge 7.x 转码依赖：仍需可复现技术方案；方案完成前允许 piper 实际承载请求，但主从定义不变
- **推荐**：按 Vange 已决执行，v0.2 Spec 全量同步

### A2. 固件↔服务音频上传协议（P1-03）
- **冲突**：路线图 F1 写"板子 opus 编码 → WiFi 上传"；语音桥 v0.1/v0.2 只收 WAV（16k）。双方按文档实现后无法联调。
- **选项**：
  - ① 服务端加 opus 解码（新增依赖，v0.2 允许？）
  - ② 板子改传 WAV（16k PCM 体积大，WiFi 流量翻几倍）
  - ③ **v0.2 锁定 WAV（现状），opus 线协议留 M1 定义接口**（推荐——v0.2 边界内不扩依赖，M1 固件开发时再定）
- **裁决要求**：选 ③ 的话，Spec 需写明"M1 线协议（opus/采样率/分帧/Content-Type/服务端解码责任）待定，v0.2 期间固定 WAV"

### A3. ASR 是否流式（P1-04）
- **冲突**：技术验证结论写"近实时 ASR、禁止整段录完上传"（v0.2 硬前提）；v0.2 Spec §3 声明"ASR 引擎不改（sherpa-onnx 锁定）"、§5.3 仍要求完整 WAV 上传。
- **选项**：
  - 方案 A：**v0.2 只做 LLM/TTS 流式，修正"全流式"表述与延迟承诺**（推荐——ASR 增量流式是另一套协议，工作量翻倍）
  - 方案 B：v0.2 新增上传流 + 增量 VAD/ASR 协议（真实近实时 ASR）
- **裁决要求**：选 A 则 Spec §1/§10 的"全流式""近实时 ASR"表述同步修正

### A4. 流式应用层分帧协议（P1-05）
- **冲突**：v0.2 Spec §5.3 要求"每 HTTP chunk = 一句完整 WAV、Content-Type: audio/wav"，但 HTTP transfer chunk 不是稳定应用消息边界（可能被代理/客户端合并拆分）；多个 RIFF 串接也不是标准单一 audio/wav。
- **选项**：
  - ① 长度前缀帧：`4字节大端长度 + WAV bytes` 循环（推荐——解析简单，ESP32 好实现）
  - ② multipart boundary（新增 mime 解析负担）
  - ③ WebSocket 二进制帧（改动大，v0.2 不必）
  - ④ 连续 PCM 流（丢句边界信息）
- **裁决要求**：选 ① 则明确 Content-Type（`audio/x-wav-stream` 或保持 `audio/wav`+说明）、帧格式、EOF 标志

### A5. open_ms 唯一权威定义（P1-06）
- **冲突**：v0.2 Spec §5.3 定义 `open_ms` = 请求到首 chunk 首字节墙钟；§6.5 又定义 = asr+llm_ttft+tts_first（分项求和漏 VAD/解析/分句等待/框架开销，会低报）；且 X-Timing-First-Token 响应头在首句生成前无法完整发出。
- **裁决要求**：
  1. 唯一权威指标 = `perf_counter(first_body_send) - perf_counter(request_received)`（墙钟）
  2. 分项（asr/llm_ttft/tts_first）仅作解释用，不作验收
  3. 实现方案：预取首句后构造响应头，或首 chunk 前内嵌 JSON 元数据（frame 0 放 timing），或响应 trailer
- **推荐**：墙钟为准 + 预取首句后发头（实现最直接）

### A6. OI 台账状态（P1-07）
- **冲突**：Open-Issues.md 中 OI-004/OI-007 为 open；v0.2 Spec §12 写"评估完成/关闭"。Spec 是未开工草案，不能提前关单。
- **裁决要求**：Spec §12 改写为"计划覆盖/待实现"；状态唯一以 Open-Issues.md 为准；实现+测试+独立确认完成后才关
