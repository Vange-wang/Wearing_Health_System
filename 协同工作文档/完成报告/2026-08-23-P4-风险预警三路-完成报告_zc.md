## 实现要点

### 任务 A：微信推送（voice-bridge 侧）

- **触发位置**：`HealthDataStore.update()` 内——连续计数恰好跨过阈值（`_over_count == alert_consecutive`）+ 冷却期外，触发瞬间推一次。**不依赖 BOX-3 轮询**（任务单要求）；不消费 `_over_count`（留给 poll_alert 轮询播报，两路消费者互不干扰，各自独立冷却时间戳）
- **异步**：`wechat_alert.py` 用 daemon 线程跑 `hermes send -t weixin:<chat_id>`（超时 30s），不进语音首字路径，失败不影响任何链路
- **日上限 5 条**：计数 + 日期持久化到 `logs/wechat_push_state.json`，跨重启生效、次日自动重置
- **配置**：`config.yaml` health 段新增 `wechat_chat_id`（o9cq8…@im.wechat，实测通道）/ `wechat_push_enabled` / `wechat_daily_limit`

### 任务 B：BOX-3 空闲轮询播报（固件侧）

- `alert_poll_task`：30s/次轮询 `GET /health/alert`，门控条件 `s_wifi_up && !s_recording && !s_talk_active && !s_alert_playing`
- 200 → 长度前缀 WAV 帧解析（复用语音帧协议 + read_exact/play_wav）→ 播报可被按键打断；204 → 静默
- 对话侧：talk_task 在播报进行时等待让位（播报因 s_cancel 立即退出），互不抢占

### 任务 C：电脑通知

- 按任务单最小化约定：仅服务端日志 + 微信推送，未做文件通知

## 实测备注（如实披露）

1. **iLink 配额限制**：首次推送失败 `iLink sendmessage rate limited; cooldown active for 30.0s`——需微信端主动给 bot 发消息刷新会话额度（Vange 操作后重试成功）。此限制为外部平台配额，推送链路本身正确
2. 验收用合成数据注入（hr=130），服务端缓存短暂持有合成值，真实上报 5s 内覆盖；如语音查询报出合成值属预期，静置后恢复
3. 误报风险提示：手指刚放上的运动伪影期（HR 瞬间 120-177）**恰好会连续 3 帧超阈值**，日常使用中可能触发误推——根因是 P1 审查已登记的 P2 遗留（HR 峰检测微动敏感，候选 LED 电流 3→6mA + 峰检测平滑）。建议该优化在 P5 腕部形态前处理，避免真实佩戴期误报
