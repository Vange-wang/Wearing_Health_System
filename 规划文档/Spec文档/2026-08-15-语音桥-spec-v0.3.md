# 语音桥服务 Spec v0.3（接入 Hermes 会话）

> 本文档为 voice-bridge v0.3 开发规格。继承 v0.1/v0.2 全部架构约束，新增「接入 Hermes 会话」能力。
> 冲突时本 Spec 优先于 v0.1/v0.2 Spec。WorkBuddy 按此实现。
>
> **起草 + 修订**：Hermes（deepseek-v4-pro）· 2026-08-15
> **决策记录**：A1~A5 已于 2026-08-15 经 Vange 拍板（见 §5），本版为正式 Spec。

---

## 1. 目标

把 voice-bridge 从「自带 DeepSeek 的独立语音服务」升级为「Hermes 的语音前端」：

- **大脑替换**：语音交互的 LLM 后端从 voice-bridge 自带的 DeepSeek，换成 Hermes（用户已跑微信 gateway 的同一实例）。
- **共用记忆/技能**：语音对话访问 Hermes 的 persistent memory + skills，与微信（iLink bot）对话共享同一份记忆——这是 v0.2 §2 锁定的验收标准「与微信共用记忆」。
- **保留流式**：v0.2 的流式能力（分句 + 逐帧 TTS + 长度前缀帧协议）不回退，ASR/TTS 继续留在 voice-bridge。

**一句话**：voice-bridge 只负责「听（ASR）」和「说（TTS + 分句流式）」，「想」交给 Hermes。

---

## 2. 阶段边界

| 阶段 | 内容 | 验收 |
|---|---|---|
| v0.2（已完成） | LLM 流式 + 分句 TTS + VAD + health | ✅ REVIEW_PASS |
| **v0.3（本文档）** | **接入 Hermes API Server，共用 memory/skills，保留流式** | **语音对话读到的记忆 = 微信对话同一份** |
| v0.4 / M1（后续） | 真机固件联调：opus 线协议 + ESP32 帧解析 + 增量 ASR | 真机端到端延迟 |

**禁止（v0.3 红线）**：
- 不改 ASR 引擎（sherpa-onnx 锁定）、不改 TTS 主从（edge 主 / piper 兜底）、不改帧协议（长度前缀）。
- 不引入未列明新增依赖（openai SDK 已在 v0.1 requirements）。
- 不在 voice-bridge 内复制 Hermes 的记忆/技能逻辑（记忆只活在 Hermes 侧）。
- **不留 DeepSeek 兜底路径**（A1 裁决：彻底停用，语音 LLM 只走 Hermes）。

## 3. 架构方案

### 3.1 接入方式：Hermes API Server（OpenAI 兼容）

Hermes gateway 内置 API Server，OpenAI 兼容（`POST /v1/chat/completions`，`/v1/models`，`/health`，支持 `stream: true` SSE）。每个请求在 API-server 主机上创建 server-side `AIAgent`，带完整工具集 + memory + skills。

- 启用：`hermes config set API_SERVER_ENABLED true` + `API_SERVER_KEY <secret>`（`/health` 在 `http://127.0.0.1:8780/health`，端口见 §3.5）
- 鉴权：`Authorization: Bearer <API_SERVER_KEY>`
- 流式：`stream: true` 返回 SSE，与 voice-bridge 现有 openai SDK 用法一致

### 3.2 组件改动（voice-bridge/）

| 组件 | v0.2 | v0.3 改动 |
|---|---|---|
| `app/llm.py` | DeepSeek（base_url=api.deepseek.com，model=deepseek-chat） | **彻底替换**为 Hermes 后端：base_url=`http://127.0.0.1:8780/v1`，model=`hermes-agent`（或 profile 名），api_key=`API_SERVER_KEY`；`stream_chat()` 保留；DeepSeek 调用路径删除，不留 fallback |
| `app/config.yaml` | `llm:` 指向 DeepSeek | `llm:` 段改指 Hermes（api_server_url / api_server_key_env / model） |
| `app/pipeline.py` | ASR→LLM流→分句→TTS→帧 | 加安抚语分支（§4），其余不变 |
| `app/asr.py` / `app/tts.py` | 不变 | 不变 |

**关键点**：Hermes API Server 是 OpenAI 兼容，voice-bridge 现有 `openai` SDK 的 `stream_chat()` 只需换 base_url/model/api_key，流水线主体零改动。

### 3.3 共用记忆（A3 裁决）

- voice-bridge 接入的 Hermes API Server 与微信（gateway Weixin adapter）跑**同一个 profile**（用户默认 profile）。
- Hermes 的 persistent memory（跨 session 的 memory 条目）是 profile 级的 → 语音对话与微信对话自然共享同一份记忆。
- **会话连续性（A3）**：语音每轮请求**独立 session，不跨轮 resume**。跨轮记忆全部由 persistent memory 承载（不靠 session 上下文），避免上下文污染与成本累积。

### 3.4 工具集裁剪（A4 裁决）

语音场景下 Hermes 只留安全轻量工具，禁重工具（防语音误触危险操作 + 场景不符 + 成本）。

| 保留 | 裁剪 |
|---|---|
| memory（记忆，核心）、skills（技能，核心）、session_search（查历史）、只读查询类（如 web_search） | terminal、file、browser、delegation、cronjob 等重工具 |

- **实现优先级**：同 profile 内**按 platform 裁剪**（语音走 API Server platform、微信走 Weixin platform），保住共用记忆。
- **待实测**：WorkBuddy 开工先验证 Hermes 是否支持「按 platform 精细裁剪工具集」。支持 → 按上述裁剪；不支持（只能全局裁）→ 立即停工上报，重新议「共用记忆 vs 工具裁剪」的平衡方案，不得擅自全局裁剪（会连带影响微信）。

### 3.5 端口与网关（v0.3 实测踩坑）

- **8642 端口在 Windows 排除端口段（8605-8704）**，API Server 绑不上（WinError 10013）→ **改用 8780**。
- Hermes gateway 是 Vange 常驻服务，重启会中断微信 bot；改配置/重启属外部动作，需 Vange 知情后再动。
- 从沙箱 bash 重启 gateway 时用干净环境绕过 safe-delete 钩子：`env -u PYTHONPATH -u PYTHONHOME -u MSYSTEM hermes gateway start`。

## 4. 流式语义与延迟口径（A2 + A5 裁决）

v0.3 的 LLM 是 Hermes agent，可能先跑工具（期间只出「工具指示」无正文 token），最后才流式出最终答案。

**延迟分段计量**：

- **纯闲聊（无工具调用）**：open_ms 定义同 v0.2（首字节 flush - 请求接收完），验收走放宽口径：**稳态平均 ≤ 4000ms**（含 Hermes agent 固定开销，A5 裁决）。
- **带工具调用**：open_ms 拆两段——
  - `tool_ms`（工具期：请求 → 工具全部跑完）：如实上报，**不卡线**。
  - `answer_open_ms`（答案期：工具结束 → 首句答案 flush）：验收卡此段，**稳态 ≤ 4000ms**。
- **流式可感**：仍是「分句逐帧到达」，沿用 v0.2 终审口径（多句回复帧数≥2 且帧间隔>0，单句豁免）。
- 结构化日志如实记录 `tool_ms` / `answer_open_ms` / `llm_backend=hermes`，不谎报 DeepSeek。

**安抚语机制（A5 裁决，短期方案）**：

- 慢路径（SSE 出现工具指示 / 记忆检索迹象）→ 先 TTS 一句安抚语（如「好的，我查一下」）作为**第一帧**发出，用户立刻有反馈，再等正式答案。
- 快路径（纯闲聊）直接答，不发安抚语。

> 延迟优化的完整三期方案（短期安抚语 / 中期轻量直通 / 长期知识库 RAG）见 `规划文档/技术验证/2026-08-15-v0.3延迟优化方案.md`。

## 6. 验收标准（v0.3 全过才算完成）

1. 语音对话由 Hermes 回答：`llm.py` 请求打到 Hermes API Server（`/v1/chat/completions`），非 DeepSeek；代码中不存在 DeepSeek 调用路径。
2. **共用记忆（核心验收）**：在微信（gateway）里写入一条 memory（如「用户喜欢 X」），语音问「我喜欢什么」，Hermes 能答出 X —— 证明语音与微信读同一份 memory。
3. 技能可用：语音触发一个已装 skill，Hermes 能调用 skill 返回结果。
4. 流式不回退：多句回复逐帧到达（帧数≥2 且帧间隔>0），单句豁免（沿用 v0.2 终审口径）。
5. 延迟口径（A2+A5）：纯闲聊 open_ms 稳态 ≤4000ms；带工具 answer_open_ms 稳态 ≤4000ms，tool_ms 如实上报不卡线。
6. 安抚语（A5）：慢路径（工具调用）先发安抚语第一帧，再发正式答案帧；快路径直接答。
7. health 如实反映后端 = Hermes（不谎报 DeepSeek）。
8. 错误路径：Hermes API Server 不可达 → 502 upstream_error（沿用 v0.1 错误码表），不崩。
9. 工具集裁剪（A4）生效：语音请求下 Hermes 无 terminal/file/browser 等重工具，只有 memory/skills/只读工具。
10. 结构化日志：记录 `llm_backend=hermes` + open_ms 分段 + 不记语音正文（C2/C5 延续）。

## 9. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| Hermes 工具调用延迟拉长开口 | open_ms 恶化 | A2 分段计量 + A4 裁重工具 + A5 安抚语 |
| 按 platform 裁剪不支持（只能全局裁） | 共用记忆与裁工具打架 | A4 前置实测，不支持即停工上报重议，不擅自全局裁 |
| API Server 与微信 gateway 并发抢 Hermes | 单实例串行瓶颈 | 实测；必要时评估并发，但不得牺牲共用记忆 |
| 语音误触危险工具 | 终端/web 误操作 | A4 工具集裁剪，禁重工具 |
| Hermes 流式含工具指示污染分句 | 分句器把「工具 emoji」当正文 | llm.py 过滤 SSE 工具指示事件，只取正文 delta |
| Hermes 自动存 memory 误记闲聊 | 记忆污染 | 实现时评估限制 memory 写（读为主），必要时 Hermes 侧配置 |
| 冷启动 47.5s 首问慢 | 首问体验差 | 查证是否可预热（延迟优化方案 §五 #3） |
