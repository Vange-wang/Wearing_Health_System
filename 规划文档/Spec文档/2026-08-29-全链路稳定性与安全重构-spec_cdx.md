## 1. 背景与目标

本次重构处理 2026-08-29 全项目审查确认的安全、测量正确性、告警可靠性、首字延迟、并发和工程复现问题。采用“内部整体重构、外部协议兼容”的路线：允许重组模块和状态机，但保留当前 BLE 数据帧、HTTP 主要路径、按键手势和长度前缀 WAV 协议。

目标：

1. 源码、Git 工作树和运行日志不包含 WiFi 密码或设备令牌。
2. 恢复已真机验证的腕带 P1 峰检测算法，并把传感器驱动、算法、质量门控和 BLE 发送解耦。
3. BOX-3 不截掉按键后前 300ms 语音，收到第一句音频后立即流式播放。
4. 健康数据只接受已认证设备的合理输入，运动或低质量数据不触发健康告警。
5. 告警在 BOX-3 播放确认和微信发送成功之前不被消费，失败后可持久化重试。
6. 服务端请求状态互相隔离，运行状态、性能打点和错误码反映真实情况。
7. 两套固件可在既有 ESP-IDF 5.2.7 环境中完整构建、烧录并留存真机证据。

## 3. 兼容性与非目标

### 3.1 必须保持

- BLE 综合健康帧的现有字节布局和 UUID。
- 现有 HTTP 主要路径和长度前缀 WAV 响应格式。

新增设备令牌请求头和告警确认接口属于兼容性安全扩展。升级采用受控过渡：服务端先部署支持 `observe`/`required` 的认证开关，过渡窗口仅允许 `observe` 并对缺失令牌限频告警；随后升级 BOX-3 并证明全部设备请求携带正确令牌；最后立即切换为 `required`。最终交付配置不得停留在兼容模式，过渡期间也不得把缺失令牌视为安全验收通过。

- 不更换 MAX30102、ESP32-C3、ESP32-S3 BOX-3 或现有音频 Codec。

## 4. 总体架构

### 4.1 腕带节点

    MAX30102Driver
      -> SampleRing
      -> P1SignalProcessor
      -> SignalQualityGate
      -> HealthFrameEncoder
      -> BLEPeripheral

- 驱动层只负责 I2C、寄存器、FIFO、采样时间和恢复。
- 算法层只接受样本快照，不直接访问 GPIO、I2C 或 BLE。
- 质量层决定 HR、SpO2 有效位和运动伪影位。
- BLE 层只编码和发送结果，不重新解释算法质量。

### 4.2 BOX-3

    CredentialStore -> WiFiManager
    BLECentral -> HealthUploader
    ButtonController -> AudioSession -> VoiceHttpClient
    AlertClient -> AudioSession

- AudioSession 是麦克风和扬声器的唯一所有者。
- 对话优先于告警；按键可原子取消告警。
- 所有跨任务状态使用互斥量、事件组或队列，不依赖 volatile bool 充当同步原语。

### 4.3 voice-bridge

    DeviceAuth
      -> VoiceSessionService
      -> HealthIngestService -> HealthStore
      -> AlertOutbox -> BoxAlertDelivery / WeChatDelivery
      -> RuntimeHealth

- HTTP 路由只做认证、校验和协议转换。
- 健康状态、告警状态、微信发送状态和语音 timing 各自独立。
- 单设备语音会话串行化，忙时返回明确错误，不共享可变请求状态。

- 设备认证令牌

现有已暴露 WiFi 密码必须由用户在路由器、学校网络和手机热点侧轮换。代码修复不能替代外部轮换。

2026-08-29 前置核实确认：`voice-bridge/config.yaml` 当前含非空 `wechat_chat_id`，该文件受 Git 跟踪，并且历史检查发现已有提交包含非空值。迁移时必须把当前跟踪文件中的完整值移出，改由本地环境配置提供；证据只记录键名、存在性、影响提交数量和必要哈希，不输出原值。Git 历史清理仍属于单独授权范围。

### 5.2 本地配置与 NVS 分区

- build_voice.py 从 Git 忽略的本地配置读取多组 WiFi 凭据和设备令牌。
- 构建时调用 ESP-IDF 5.2.7 的 NVS 分区生成工具，生成临时 NVS 镜像。
- NVS 数据模型使用独立键：凭据数量、逐项 SSID、逐项密码、优先级、认证类型和设备令牌；不把编译器结构体内存布局作为持久化格式。
- 构建日志只记录条目数量、目标分区和镜像哈希，不记录值。
- build_voice.py 在应用构建成功后，根据分区表确定 NVS 偏移，将应用和本地 NVS 镜像烧录到 COM5。
- 本地配置和生成的 NVS 镜像必须被 D:\esp-box\.gitignore 忽略。
- `wechat_chat_id` 从受 Git 跟踪的 `config.yaml` 移至 voice-bridge 本地环境配置；跟踪配置只保留空值或环境变量说明，不保留真实接收标识。

### 5.3 源码凭据移除

- 删除 DEFAULT_WIFI_CREDS 及所有真实凭据副本。
- NVS 缺失或损坏时进入明确的“未配置”状态，不回退到源码默认值。
- NVS 读取必须压紧有效条目，不能因中间键缺失产生未初始化空洞。
- 复制到 wifi_config_t 时执行长度校验并显式终止，禁止无界 strcpy。

### 5.4 设备认证

- BOX-3 对设备接口发送 X-Device-Token。
- voice-bridge 从环境变量读取服务端令牌，使用恒定时间比较。
- 缺失令牌返回 401，错误令牌返回 403；响应不得说明令牌长度或内容。
- 认证覆盖健康上报、告警轮询与确认、BOX-3 语音上传接口；公开运行状态接口不返回敏感配置。
- 认证模式只允许 `observe` 和 `required`：`observe` 仅用于同批升级的短暂过渡并记录无敏感内容的缺失令牌告警，`required` 执行上述 401/403 语义。BOX-3 升级验证后必须切到 `required`，否则设备认证 finding 不得标记修复。

## 6. 腕带固件重构

### 6.1 P1 算法恢复

- 以指定 P1 纯峰检测版和 10 秒窗口恢复算法；生产候选 LED 暂定 0x17，以 §6.4 判定结果为准，不预设最终算法与 LED 组合。
- 保留现有公开 hr_spo2 API，必要时只增加质量字段，不改变 BLE 帧布局。
- 当前自相关实验版不继续作为生产路径，已有 Git 历史作为保留证据。
- 算法每次只处理最近的完整窗口；快照时在临界区复制，计算时不长期持锁。
- 旧峰检测与 0x0F 是 E0 参考组合；旧峰检测与 0x17 是 E1 未验证组合；4.6mA 下的四重门限版 bd9e564 是 E2 对照候选。三者不得混淆验收结论。

### 6.2 时间与窗口

- 时间差使用无符号回绕安全计算，不能用 end > start 判断。
- 采样率超出合理范围时标记本窗口无效并记录限频诊断，不用静默固定值伪装有效测量。
- 数据不足时返回无效标志，不复用未经标注的旧测量值。

### 6.3 MAX30102 驱动

- 成功读写均重置连续失败计数；失败才递增。
- 初始化和恢复过程检查每个关键寄存器写入结果。
- 任何关键配置失败时不得打印“初始化完成”或返回成功。
- 读取并处理 FIFO 溢出计数；溢出后清空受污染 FIFO，当前算法窗口作废。
- 总线恢复有明确成功或失败结果；连续恢复失败进入退避重试，不形成忙循环。
- 初始化、NVS、BLE、LED 和任务创建结果均检查；非关键 LED 失败可降级，传感器或 BLE 失败必须可观测。
- 临时原始样本转储默认关闭，只能通过显式诊断开关启用，并限频输出。
- 驱动可靠性修改仅限错误传播、FIFO 溢出处理、恢复结果和可观测性；LED 电流、采样率、脉宽、ADC 范围、FIFO 平均和采样模式等采样参数必须在改动前后逐项对照并保持一致。
- Task 7 驱动验证完成且采样参数对照通过后，才允许进入 Task 8；E0/E1/E2 不得与驱动重构并行执行。

### 6.4 信号质量受控实验与判定

批次 2 必须保留可开关诊断打点，记录 LED 电流、采样率、IR/RED 的 DC 与 AC 幅度、心跳频带能量占比、算法质量指标、HR/SpO2 输出及有效标志。诊断数据不得混入正常运行日志。

受控实验按固定顺序执行：

1. 在任何 E0 烧录前，先由用户配合完成清洁传感器窗口和手指、遮挡环境杂光、固定同一手指与压力的物理预检，并准备外部血氧仪作同步参照。
2. E0：旧峰检测、10 秒窗口、LED 0x0F，验证已知良好组合能否恢复。
3. E1：只把 LED 改为 0x17，其他条件不变，观察 AC 幅度、微动假跳和参考误差。
4. E2：如 E1 出现微动假跳，再使用 bd9e564 四重门限与 0x17 对照；不得同时改变窗口、接触方式或其他滤波参数。
5. 每组至少记录稳定静置、轻微手指移动和重新佩戴三种场景，不凭单次读数裁决。

物理配合是 Task 8 Step 2-4 的硬门：没有用户现场完成同一手指、近似固定压力、外部血氧仪同步读数和规定动作时，实验只能标记“等待物理配合”，不得执行替代实验或标记通过。

判定规则：

- E0 通过而 E1 失败：保留 E0 证据并进入 E2；不得自行把生产配置改回 0x0F。
- E0、E1 均通过：生产配置继续使用既定 0x17。
- E1 微动失败而 E2 通过：可选择 bd9e564 四重门限与 0x17，但必须记录相对 E0 的首个有效值时间和误差，不得以增加输出等待换取表面稳定。
- E1、E2 均失败：生产候选 0x17 未通过，停止继续叠加算法门限并向用户提交裁决，不自行切换最终 LED 配置。
- E0 也失败：判定为当前光路、接触、模块个体或硬件状态阻塞，停止叠加算法补丁；保留原始数据并转入物理排查，不把批次 2 代码标记为真机通过。
- 物理衰减根因不要求由本软件重构修复，但必须被独立标注，不能归因成算法失败或用伪造有效值绕过验收。

## 7. BOX-3 固件重构

### 7.1 按键与首段语音

- 按键按下立即开始采样，将前 300ms 写入固定大小预缓冲。
- 持续达到长按阈值后建立 HTTP 请求，先发送预缓冲，再发送实时采样。
- 阈值前释放则丢弃预缓冲，保留短按与双击手势且不产生空 HTTP 请求。
- 预缓冲必须静态或一次性分配，不能在实时音频循环中反复申请堆内存。

### 7.2 流式播放

- 保留 4 字节大端长度前缀和每帧独立 WAV。
- 读到 WAV 头并验证 PCM 参数后，按固定块直接写入 Codec；禁止等待整帧下载完成。
- 固件帧长上限与服务端 8MB 配置一致，同时以音频时长和可用堆内存做第二道约束。
- HTTP、Codec 和内存操作必须检查短写、短读和错误码。
- 单句中断只结束当前会话，释放全部资源并恢复下一次请求能力。

### 7.3 音频仲裁

- 对话、告警和取消事件经过同一个 AudioSession 状态机。
- 告警发起网络请求前先申请播放资格；用户按键可以取消租约和播放。
- 不允许告警下载与对话同时操作共享音频缓冲。

### 7.4 BLE 中央

- CCCD 写入两字节小端 0x0001 并检查完成结果。
- 描述符发现使用完整合法句柄范围，不假定 CCCD 一定紧邻特征值。
- 持久化对端地址和地址类型，重连时按原地址类型连接。
- 广播能力位必须同时满足当前产品要求的 HR 与 SpO2 能力。
- 断线时立即使缓存失效；重连第一帧重建序号基线，不计入历史丢帧。
- 运动伪影、HR 有效和 SpO2 有效标志随健康上报传给服务端。

## 8. voice-bridge 重构

### 8.1 输入校验与资源限制

- HR 只接受 20 至 250 BPM；SpO2 只接受 50% 至 100%；序号只接受协议范围内整数。
- 健康上报必须包含质量标志；无有效生理字段的帧只更新链路状态。
- WAV 和 raw PCM 上传在读取过程中累计字节数，超过配置上限立即返回 413。
- raw PCM 必须是完整 16-bit 样本，奇数字节结尾返回输入错误，不静默截断。

### 8.2 健康数据新鲜度

- HR、SpO2 和链路分别保存时间戳。
- 单字段无效不会刷新另一个字段的新鲜度。
- 字段超过 5 分钟时查询返回该字段中断；任何字段超过 30 分钟均不得参与预警。
- 运动伪影或质量不合格帧不累计连续异常次数。

### 8.3 告警状态机

- 告警事件至少包含不可重复 ID、生成时间、数值快照、质量、各通道状态和重试时间。
- 持久化状态为 pending -> leased -> acknowledged；租约超时回到 pending。
- BOX-3 轮询获得告警时服务端先完成 TTS，再创建播放租约，并在响应头返回告警 ID。
- BOX-3 播放完成后调用新增确认接口；未确认、连接中断或播放取消均不消费告警。
- 重复确认保持幂等。
- 告警文件采用原子替换写入，并限制保存数量和保留天数。

### 8.4 微信发送

- 微信发送成功后才增加日计数并完成该通道。
- 失败保留告警，采用有上限的指数退避；达到日上限后延迟到次日，不丢弃。
- 进程重启后恢复未完成事件和当天成功计数。
- 日志记录告警 ID、错误类别和重试时刻，不记录完整接收标识。

### 8.5 语音请求与并发

- 每个请求创建独立 timing、路由结果和分句缓冲。
- 单 BOX-3 场景用显式会话锁串行化 ASR、LLM、TTS，忙时返回 409 device_busy。
- 同步网络打开动作不得在事件循环中执行；必要时放入工作线程。
- LLM 客户端复用连接并检查 HTTP 状态码。
- TTS worker 对所有异常发送终止信号，任何 worker 异常不得让重排循环永久等待。
- 并行 TTS 数量由配置限定，默认值以首字延迟和稳定性实测确定，不预设越多越快。

### 8.6 分句、记忆和运行状态

- SentenceBuffer 保留跨增量片段的空格和换行；只在完整句边界清理 Markdown。
- MemoryClient 从文件尾部定长读取，不能为 6KB 注入读取整个 MEMORY.md。
- /api/v1/health 只有在必需组件可用时返回 ok；部分组件不可用返回 degraded。
- timing 明确区分服务端首帧生成、首字节写出和固件首音频播放；不得把后续 TTS 或句间停顿计入 LLM 总耗时。

### 8.7 看门狗

- Windows 进程检查使用命令行或 PID 文件，不用 tasklist 的映像名称搜索脚本参数。
- mDNS、voice-bridge 和 memory server 各自只有一个所有者和 PID 记录。
- 看门狗检测运行状态而非仅检测端口，日志启用大小和数量轮转。

## 9. 测试策略

### 9.1 确认的测试缝隙

- 腕带：hr_spo2_process() 的确定样本输入与结果；IDF 完整构建；COM6 真机串口。
- BOX-3：BLE 帧解析、WAV 帧解析、NVS 加载、音频会话状态机；IDF 完整构建；COM5 真机串口。
- 服务端：FastAPI HTTP 接口、HealthDataStore、告警出站箱、微信适配器、分句器。
- 安全：设备认证和输入校验的恶意与合法对照。
- 延迟：同条件记录改动前后首帧与首音频数据。

### 9.2 TDD 规则

- 每个行为先写一个从公开边界观察的失败测试，再写最小实现。
- 一次只完成一个红—绿闭环，不先批量写完所有测试。
- 回归测试必须验证修复前会失败、修复后会通过。
- 不用空 pass、永久 skip 或只断言状态码存在代替行为验证。

### 9.3 自动化验收

必须覆盖：

1. 缺失、错误和正确设备令牌。
2. HR、SpO2、序号边界和越界输入。
3. HR 更新不刷新 SpO2 时间戳。
4. 持续异常经过冷却后可再次生成告警。
5. TTS、下载和播放未确认时告警仍存在。
6. 微信失败不消耗日配额，重启后仍可重试。
7. “Hello” 与 “ world.” 分片仍得到 “Hello world.”。
8. 超长音频、奇数字节 PCM 和并发语音请求。
9. 断连后 BLE 缓存失效，重连序号不产生虚假丢帧。
10. NVS 中间条目缺失时有效条目仍被压紧加载。

### 9.4 真机验收

腕带 COM6：

- 完整构建和烧录成功。
- Part ID 和关键寄存器配置确认成功。
- 连续运行期间无 I2C 忙循环、无 FIFO 溢出未处理。
- 先按 §6.4 完成 E0、E1，必要时完成 E2，并保存受控实验数据。
- 指尖稳定场景可在既有 P1 验收范围内给出 HR 与 SpO2；运动场景正确标记无效或伪影。
- 若 E0 因物理信号衰减失败，批次 2 状态记为“代码构建通过、真机信号阻塞”，不得写成算法或整批验收通过。
- E0/E1/E2 的佩戴、压力控制、轻微移动、重新佩戴和外部血氧仪读数必须由用户现场配合；缺少该配合时停在验收门前。

BOX-3 COM5：

- 应用与本地 NVS 分区烧录成功，源码中无凭据仍可连接目标 WiFi。
- BLE 能订阅并接收腕带综合帧，断线重连后恢复。
- 短按不发空请求，长按开头语音不被截断。
- 语音问答首帧和首音频延迟不劣于同条件改动前基线。
- 告警播放完成后确认；播放中按键可取消且告警随后可重试。

串口前置条件：

- 进入烧录步骤前重新枚举串口；COM5 或 COM6 缺失时，真机步骤记为等待硬件连接，不改用 COM3 或 COM4 蓝牙虚拟口。
- 串口缺失不阻止源码测试和离线构建，但不得据此宣布对应真机验收通过。

端到端：

- 模拟异常数据必须经过合法令牌和质量门。
- BOX-3 播报与微信通道分别确认，不因另一通道失败而丢失。
- 服务重启后未完成告警仍在。

## 10. 首字延迟门

任何业务源码改动前，必须在 Task 1 使用当前未改固件，在同一网络、同一服务配置、同一测试语句下完成至少 5 轮基线。若 COM5、服务端或必要观测条件不可用，后续源码任务停止等待，不允许把基线延后到重构完成后。每轮至少记录：

- 按键释放到服务端收到请求结束
- ASR final
- LLM 首 token
- 首句 TTS 完成
- 首帧首字节写出
- BOX-3 收到首帧
- Codec 写入首批 PCM

验收以端到端墙钟为准。重构后中位数不得变慢；若波动明显，补充不少于 10 轮并比较 P95。任何新增安全或状态检查必须位于非首字关键路径，或有实测证明成本可忽略。

## 11. 实施批次与回滚

1. 改动前证据：当前未改固件的至少 5 轮七点首字延迟基线、仓库状态、哈希、补丁和服务端测试基线；未通过该门不得开始业务源码改动。
2. 安全和构建基线：本地 NVS、源码去密、设备认证、输入校验；认证按 `observe` → BOX-3 携令牌 → `required` 顺序切换。
3. 腕带：恢复 P1 与诊断接口；串行完成驱动可靠性并证明采样参数未变；等待用户物理配合后执行 E0/E1/E2 受控实验和 COM6 验证。
4. BOX-3：音频会话、BLE 中央、健康上报、COM5 验证。
5. 服务端：健康状态、告警出站箱、微信重试、语音并发与性能。
6. 工程收尾：看门狗、模型与日志与依赖、README、Word、交接证据和归档同步。

每批必须具备独立回滚点：保留修改前文件哈希和补丁；失败时只回滚本批点名文件，不触碰 D:\esp-box 其他用户改动。不得使用 git reset --hard 或覆盖整个工作树。
