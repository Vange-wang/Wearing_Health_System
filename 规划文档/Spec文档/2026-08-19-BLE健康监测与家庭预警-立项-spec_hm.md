# BLE 健康监测 + 家庭预警 立项 Spec

- **起草**：Hermes（deepseek-v4-pro）· 2026-08-19
- **依据**：毕设起草书（BLE 传感网络）+ `2026-08-17-BLE健康监测-实现路径与问题假设_hm.md`（28 问题假设）+ 微信推送实测（hermes send → weixin 单向已通，iLink 配额 24h/10 条）
- **实施**：zcode（开发员）
- **场景**：家庭健康监护——检测端在老人身上，BOX-3 老人日常对话，预警三路（BOX-3 告知老人 + 手机微信提醒子女【主】+ 电脑通知【辅】）

---

## 1. 目标

腕部检测节点（心率/血氧）通过 BLE 接入 BOX-3，数据经 WiFi 到 PC 服务端，实现：
1. 老人语音查询健康数据（「我的心率多少」→ 真实数据，替代「即将上线」）。
2. **风险预警三路推送**：BOX-3 语音告知老人 + 手机微信提醒子女（主通道）+ 电脑端 Hermes 通知（辅）。

## 2. 架构

```
[腕部节点] 老人佩戴(ESP32-C3 + MAX30102 心率/血氧)
    ↓ BLE（GATT 连接，NimBLE，周期采样上报）
[BOX-3] 老人使用（BLE central 接收）
    ├→ 预警①：BOX-3 空闲轮询取预警音频播放 → 告知老人（下行通道见 §5.1 方案 A）
    └→ WiFi POST /api/v1/health/data
[PC voice-bridge] 健康数据接口 + 风险分析
    ├→ 语音查询路由（"心率多少"→ 真实数据）
    ├→ 预警②：hermes send → 微信 iLink → 提醒子女（单接收方：bot 绑定的微信）
    └→ 预警③：电脑端 Hermes 通知（辅）
```

## 3. 实现路径（P1-P4）

| 阶段 | 内容 | 产出 |
|---|---|---|
| **P1** | 腕部节点固件：MAX30102 采集（指尖式验证，数据准）+ BLE peripheral | 心率/血氧能通过 BLE 发出 |
| **P2** | BOX-3 加 BLE central：扫描连接腕部节点，接收数据 + 解析缓存 | BOX-3 能拿到心率/血氧 |
| **P3** | 数据流 + 语音查询：BOX-3 → WiFi → PC 健康接口 + **DATA 路由（优先级高于 RAG）+ 模板直答** | 语音问"心率多少"→ 真实数据（非静态科普） |
| **P4** | 风险预警三路：阈值分析 + BOX-3 播报 + 微信推送 + 电脑通知 | 家庭预警闭环 |
| P5（扩展）| 腕部形态（老人佩戴，信号弱调优）+ 多节点（ECG/体温） | 完整可穿戴 |

## 4. 关键技术决策

| # | 决策点 | 裁决 |
|---|---|---|
| 1 | 腕部节点硬件 | ESP32-C3 小板（~¥15，BLE 够用）+ MAX30102 成品模块（心率/血氧二合一，免焊接） |
| 2 | 测量方式 | **P1 指尖式验证**（MAX30102 设计给指尖，数据准）；P5 过渡腕部（老人佩戴形态，信号弱 + 运动伪影二期调优） |
| 3 | BLE 栈 / 模式 | NimBLE + GATT 连接模式（持续传输可靠） |
| 4 | GATT 服务 | 心率标准服务 0x180D（0x2A37）+ 血氧自定义服务（自定义 UUID） |
| 5 | 数据模式 | 周期采样（每 5s 一组 → 发送 → 休眠，续航优先） |
| 6 | 配对 | 首期 Just Works（无密码，快速打通），NVS 存对端 MAC 直连 |
| 7 | 数据接口 | voice-bridge 加 `POST /api/v1/health/data`（接收）+ 最新值缓存（供查询/预警） |

### 4.1 DATA 路由（P3 硬前置，防 RAG 截胡）

- **实测**：`KnowledgeBase.search('我的心率多少', score_threshold=1.0)` 命中「心率正常范围」静态科普（2026-08-19 zcode 实测）——不加 DATA 路由，P3 上线后真实数据查询会被 RAG 截走，答非所问。
- **规则**：新增 DATA 路由位，排在 RAG 之前——「心率/血氧/我的/现在/当前/多少」等真实数据查询关键词命中 → 健康数据模板直答。
- **回答方式**：**模板直答 + TTS**（「您当前心率 78，属于正常范围」），不经 LLM——数据类回答要确定性（LLM 有读错数/编数风险），且模板直答首字更快。若未来要 LLM 润色，必须数据注入提示词。
- **SYSTEM_PROMPT 第 5 条改造**（`llm.py:49`「尚未接入」兜底）：改为条件化——有数据时答真实值，无数据时（>5 分钟）答「检测暂时中断」，不再永远「即将上线」。

## 5. 预警机制（P4 核心）

### 5.1 风险判定（两级）

- **阈值级**（voice-bridge 做，规则可配）：心率 >100 或 <50、血氧 <95%；**夜间（23:00-6:00）心率下限下调至 <45**（老人睡眠心率 45-55 常见，防误报）。
- **智能级**（Hermes 做，后续）：趋势判断 + 结合用户描述（"心率持续走高 + 胸闷"→ LLM 综合建议）。

**预警①下行通道（方案 A：BOX-3 空闲轮询）**：
- BOX-3 固件加空闲轮询 `GET /api/v1/health/alert`（每 30~60s）；
- 服务端有预警时直接返回 WAV 帧（复用现有帧协议），BOX-3 播放后继续轮询；
- 阈值单点在服务端（可配），固件只加轮询，改动最小；预警延迟 = 轮询间隔（30-60s，连续监测场景可接受）。

### 5.2 防误报

- 连续 3 次采样超阈值才触发（单次波动不警）。
- 触发后冷却 10 分钟（不重复轰炸）。
- 阈值保守（>100 才警，正常运动/情绪波动不误报）。

### 5.3 三路推送

| 通道 | 接收方 | 内容 | 限制 |
|---|---|---|---|
| BOX-3 语音播报 | 老人 | 「小V提醒您，心率 128 有点偏高，建议坐下来休息一下」 | 无（本地，最可靠） |
| **微信 iLink（主）** | 子女手机（**bot 绑定的单个微信**，扫码登录） | 「健康提醒：您父亲心率 128 持续偏高，建议关注」 | **iLink 配额 24h/10 条**（子女互动激活） |
| 电脑 Hermes 通知 | 子女电脑 | 同上 | 无 |

### 5.4 微信推送可靠性（主通道，重点设计）

- **发送方式**：`hermes send -t weixin:<chat_id> "<预警消息>"`（已验证单向通，需网关运行）。
- **配额保障**：子女作为监护人日常互动多（每次互动重置 10 条配额），主通道可用性高；但仍设计降级。
- **降级机制**：推送失败（限流/配额耗尽）→ 预警留存 → 子女下次互动时 Hermes 补报（"对了，您父亲今天下午心率有几次偏高"）。
- **单接收方（iLink 限制，已查证）**：iLink bot 绑定在「扫码登录的那个微信」，其他微信无法添加 bot（无微信号可搜索）。**扫码登录必须用子女/监护人的微信**——微信预警只推给这一个接收方；老人不需要微信（BOX-3 语音 + 语音查询覆盖）。
- **微信日上限 ≤5 条**：防误报 10 分钟冷却 + 日上限双保险——最坏 6 条/小时也 1.7 小时才接近上限，不会耗尽全天 10 条配额；超限后只走 BOX-3 + 电脑端，次日汇总补报。
- 预警消息合并（避免分割消耗配额）：单条消息 ≤2000 字。

## 6. 验收标准

1. P1：腕部节点 BLE 发出心率/血氧（指尖式验证，与指尖血氧仪对比误差 ±3% 内）。
2. P2：BOX-3 BLE central 连接腕部节点，收到数据（日志/调试可见）。
3. P3：语音问「我的心率多少」→ 返回真实心率（非「即将上线」）。
4. P4：模拟心率超标（阈值调低测试）→ BOX-3 播报 + 微信收到预警 + 电脑通知（三路齐发）。
5. 防误报：单次波动不触发；触发后 10 分钟冷却。
6. 微信降级：手动模拟推送失败 → 预警留存 → 下次互动补报。
7. 数据新鲜度：>5 分钟无新数据，语音查询答「检测暂时中断」；>30 分钟无数据，预警功能自禁用（防陈旧数据误警）。

## 8. 风险

| 风险 | 缓解 |
|---|---|
| A2 腕部信号弱（最终形态老人佩戴） | P1 指尖式验证（数据准），P5 腕部调优；运动伪影标注"可能不准" |
| D1/D2 心率/血氧算法不准 | 现成库 + 指尖血氧仪校准（±3%） |
| iLink 配额限制（主通道） | 降级补报 + 子女互动激活；Telegram 备选（无限制，如要可靠远程） |
| 微信单接收方（iLink 限制） | 扫码登录绑定子女微信；多手机推送不可行（Hermes 单 adapter，iLink 协议限制） |
| BLE + WiFi 共存（BOX-3） | 语音优先，BLE 数据后台收（分时） |
| 老人佩戴不习惯/数据中断 | 断线重连 + "数据中断"提示 |
