## 1. 目标

在 v0.1 非流式基础上实现**流式回复**：DeepSeek 流式输出 + 分句 TTS 流水线，开口延迟 ≤ 1.5s（PC 侧服务端流水线，实测 1.2~1.4s）。同时覆盖 v0.1 CONDITIONAL_PASS 遗留 Open Issues（OI-001/004/007）并完成 v0.1 证据门补强（C1~C5）。

**范围澄清（A3 裁决）**：v0.2 只做 **LLM/TTS 流式**，ASR 保持**完整 WAV 批式识别**，不做增量/流式 ASR。"流式语音交互"在本阶段指"流式回复"——用户听到第一句时 LLM 尚未生成完整回复，与 ASR 是否增量无关。增量 ASR 属 M1 真机端到端优化，留待 M1 线协议确定后独立评估。

## 5. 接口定义

### 5.1 GET /api/v1/health（v0.2 改造 — OI-001）

返回示例：

```json
{
  "status": "ok",
  "asr": "ready",
  "tts": {
    "configured_primary": "edge",
    "active_engine": "piper",
    "fallback_reason": "edge_403"
  },
  "vad": "enabled"
}
```

规则：

- `tts.configured_primary`：配置主引擎（固定 `edge`，产品策略）。
- `tts.active_engine`：当前实际可用引擎（`edge` / `piper`）。落到 piper 仅代表 fallback 生效，**不代表主从策略改变**。
- `tts.fallback_reason`：仅当 fallback 生效时出现（如 `edge_403` / `edge_timeout` / `edge_unavailable`）；主引擎正常时省略。
- `vad`：`"enabled"` | `"disabled"`（取决于 config.yaml）。
- 启动时探测 edge-tts 连通性（发最小静音合成请求，超时 3s），不可用时 `active_engine=piper` + `fallback_reason`，health 始终反映真实状态。

### 5.2 POST /api/v1/voice/chat（v0.1 行为保留，不变）

非流式，完全向后兼容。v0.1 代码不改。WorkBuddy 不用动。

### 5.3 POST /api/v1/voice/chat/stream（v0.2 新增）

- 请求：同 v0.1 —— `multipart/form-data`，`audio` = WAV（16kHz/16bit/mono，≤15s）
- 响应：`Transfer-Encoding: chunked`，**应用层分帧（长度前缀帧，A4）**：
  - 每帧 = `[4 字节大端 uint32 长度 N]` + `[N 字节 = 一句完整 WAV 文件（RIFF header + 16kHz/16bit/mono PCM）]`
  - 客户端按帧解析：读 4 字节长度 → 读 N 字节 → 播放该句，逐帧循环
  - **EOF = HTTP 响应体结束**（无哨兵帧）
  - 最大帧长上限（默认 8MB，config 可调），服务端强制守卫，防损坏长度前缀导致客户端巨额分配
- 响应头：
  - `Content-Type: application/octet-stream`（body 是帧串联，不是合法单一 WAV，**不得用 audio/wav**）
  - `X-Audio-Framing: wav-length-prefixed`（自描述分帧协议）
  - `X-Timing: {"open_ms":..., "asr_ms":..., "llm_ttft_ms":..., "tts_first_ms":...}`（首句 TTS 完成后、发送响应头前已知；见 §6.5）
- 错误：同 v0.1 错误码表（§5.4），流式错误时 HTTP 状态码在第一个帧前发出

流式处理流程（详见 §6）：

```
WAV 上传 → VAD 预检 → ASR(批式) → LLM 流(chunk) → 句子缓冲器 → 触发条件满足 → TTS → 长度前缀帧发送
                                                                                    ↓
                                                                        ESP32-S3 逐帧播放(M1)
```

### 5.4 错误码表（v0.1 继承，v0.2 追加）

| 场景 | 状态码 | 响应 | 备注 |
|---|---|---|---|
| VAD 检测到静音/无效语音 | 400 | `{"error": "no_speech"}` | v0.2 新增（OI-007） |
| 损坏 WAV / 解析异常 | 400 | `{"error": "bad_audio_format"}` | v0.2 补强（C1，原落 502） |
| ASR 失败 / 无有效语音 | 400 | `{"error": "no_speech"}` | 继承 v0.1 |
| 音频格式不合规 | 400 | `{"error": "bad_audio_format"}` | 继承 v0.1 |
| 音频超过上限 | 413 | `{"error": "audio_too_long"}` | 继承 v0.1（上限 15s） |
| API key 未配置 | 500 | `{"error": "config_error", "detail": "..."}` | 继承 v0.1 |
| 服务未就绪 | 503 | `{"error": "service_unavailable"}` | 继承 v0.1 |
| LLM/TTS 上游失败 | 502 | `{"error": "upstream_error", "detail": "..."}` | 继承 v0.1；流式下首句前失败按此返回 |

## 6. 流式流水线设计（核心）

### 6.1 组件职责

| 组件 | 文件 | 职责 |
|---|---|---|
| `VADGate` | `app/vad.py` | 能量 RMS 阈值检测，决定是否继续走 ASR（≤rms_threshold → no_speech） |
| `SherpaOnnxASR` | `app/asr.py`（不改） | WAV → 文本（批式，已有） |
| `DeepSeekLLM.stream_chat()` | `app/llm.py`（新增） | 用户文本 → 流式 `Iterator[str]` |
| `SentenceBuffer` | `app/splitter.py`（新增） | 接收字符流，按标点/长度触发分句 |
| `TTSEngine` | `app/tts.py`（改造） | 文本 → WAV bytes（edge 主 / piper 兜底，同步合成） |
| `StreamingPipeline` | `app/pipeline.py`（新增） | 串联以上组件，产出长度前缀帧 `Iterator[bytes]` |

**解码接缝（A2）**：流水线契约是"PCM 16kHz/16bit/mono 进入 VAD/ASR"，而非"WAV 文件进入"。v0.2 输入是完整 WAV（PC 侧），M1 时在 VAD 前插 opus→PCM 解码层即可，流水线主体不动。

### 6.2 分句规则（SentenceBuffer）

```
触发条件（任一满足即输出当前 buffered 文本为一句）：
1. 遇到标点：。！？〜 ；\n（中日英共用标点）
2. 缓冲区长度 ≥ 50 字符（长句保护，避免 LLM 不发标点时永不输出）
3. LLM 流结束：flush 剩余内容（即使无标点）

连续标点合并：多个连续标点仅算一次分割。
空句子跳过：纯标点/空白不触发 TTS。
```

### 6.4 VAD 能量门限（OI-007 计划覆盖）

```yaml
vad:
  enabled: true
  rms_threshold: 0.005    # 0~1，建议值 0.005；纯静音 rms ≈ 0.001~0.003
  min_speech_frames: 10    # 连续 speech 帧数下限（frame = 10ms），低于此 → no_speech
```

实现：

- 读取 WAV float32 samples → 分帧（10ms/frame，160 samples @ 16kHz）→ 每帧 RMS
- 连续 speech frame 数 ≥ `min_speech_frames` → 走 ASR；否则 → 400 `no_speech`
- 零新增依赖：numpy 已在 sherpa-onnx 依赖链中

### 6.5 流式打点与 open_ms（A5 裁决）

**open_ms 唯一权威定义**：

```
open_ms = perf_counter(首字节 flush 到客户端) - perf_counter(请求体完整接收)
```

- 服务端墙钟，用 `time.perf_counter` 单调钟，分项求和一律不作验收。
- 分项（`asr_ms` / `llm_ttft_ms` / `tts_first_ms`）仅作解释，不参与 ≤1.5s 判定。

**实现方案（预取首句后发头）**：

1. ASR → LLM 流（缓冲到首句完整）→ 首句 TTS → 此时 open_ms 已知
2. 发送响应头（含 `X-Timing`）+ 首帧 → 继续流式处理后续句子
3. 全量 timing（见下）在响应过程中累积，流结束时写入结构化日志

**全量 timing（走日志 + 自测报告，不进响应头）**：

```
timing = {
  "asr_ms": ...,        # ASR 耗时
  "llm_ttft_ms": ...,   # LLM Time-To-First-Token
  "llm_total_ms": ...,  # LLM 全流完成耗时
  "tts_first_ms": ...,  # 第一句 TTS 耗时
  "tts_total_ms": ...,  # 全部 TTS 总耗时
  "open_ms": ...,       # 开口延迟（唯一权威，= 墙钟定义）
  "total_ms": ...,      # 全链路总耗时
  "sentence_count": ...,# 分句数量
  "chunk_count": ...,   # 发送帧数
}
```

**诚实边界（必须写死）**：`open_ms ≤ 1.5s` 仅在 **PC 本地条件（v0.2 交付环境）** 成立——完整 WAV 上传可忽略、无网络 RTT。真机（M1）WAV 上传本身即数秒，端到端开口延迟需用 opus 线协议重新预算，**不得用本 Spec 的 1.5s 验收真机**。

## 9. 验收标准（v0.2 全过才算完成）

### 9.1 功能验收

1. `POST /api/v1/voice/chat/stream` 返回长度前缀帧流，每帧可独立解析为一句 WAV
2. 开口延迟 ≤1.5s（三句实测平均 `open_ms` ≤ 1500ms，墙钟定义；PC 侧），目标 1.2~1.4s
3. 流式可感：第一个帧和最后一个帧到达时间差 ≥ 1s（证明不是等完整回复）
4. health 返回 `configured_primary=edge` + `active_engine` + `fallback_reason`（fallback 时）+ VAD 状态
5. 静音/VAD 拦截：纯静音 WAV → 400 `no_speech`（不走到 LLM，节省 token）
6. 损坏 WAV → 400 `bad_audio_format`（C1，原落 502）
7. backward compat：`POST /api/v1/voice/chat`（v0.1 路径）行为不变
8. edge 故障注入 → 自动切 piper 且不崩（C4 措辞：断网兜底 → edge 故障注入兜底，真断网 DeepSeek 也失败）
9. 请求级结构化日志覆盖成功与失败路径，不记健康语音正文（C2/C5）

> **口径裁决（2026-08-15 Hermes，依据《2026-08-15-v0.2自测报告-口径裁决报告》）**：
> - **第 2 项（open_ms）有条件接受口径**：验收对象 = 稳态三句平均，剔除服务重启后首句冷启动离群（归入 §11「峰值超标不计入 fail」）；达标线 = 稳态平均 ≤ 1600ms（1500ms + 6.7% 容差）；归因约束 = 超标须能归因 DeepSeek 首 token（`llm_ttft_ms` 为最大单项），若 llm_ttft ≤500ms 而 open_ms 仍 >1600ms 视为流水线自身缺陷打回优化。
> - **第 3 项（流式可感）指标修正（终稿）**：流式真实性 = **多句回复下逐帧到达**（帧数 ≥2 且帧间隔 >0）；单句回复（帧数=1）豁免全部流式判据（一句即完整回复，无「流式」可言）。原「首末帧间隔 ≥1s」与「open_ms ≪ total_ms」均为多句回复的量化代理指标，在回复 ≤50 字约束下均不成立，统一废除，改以「多句逐帧到达」定性判据（实测轮A-01/03 间隔 258/298ms + stream_done 日志 sentence_count≥2 且 tts_total>tts_first）。

## 10. 延迟预算（v0.2 目标，PC 侧）

```
VAD        0.02s  （能量计算，numpy 向量化）
ASR        0.25s  （SenseVoice 批式，不变）
LLM TTFT   0.50s  （DeepSeek 首 token，目标值）
分句等待   0.15s  （等首句完整 + 首句 TTS 前置）
TTS first  0.15s  （piper 首句，短句 5~15 字）
─────────────────
open_ms ≈  1.07s  （理论最佳）
实测目标    1.2~1.4s（含网络抖动 + 分句等待）
```

与 v0.1 对比：v0.1 等待完整 LLM 回复（2~3s），v0.2 只等首 token + 首句，开口延迟从 2-4s 缩短至 ~1.2s。

> 口径澄清（A3/A5）：本预算为 **PC 本地服务端流水线**，不含真机 WAV 上传/网络 RTT；ASR 为批式（完整 WAV），非增量。

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| DeepSeek 首 token 延迟波动（0.4~1.5s） | 开口延迟超标 | v0.2 只要求平均 ≤1.5s；峰值超标不计入 fail |
| 分句等不到标点（LLM 长句无句号） | 首句永远不发 | 长句保护 50 字符硬切割 |
| edge 持续 403 | piper 实际承载，音色略降 | edge 恢复评估任务独立推进（§6.3）；health 如实上报 |
| piper 音色不如 edge 自然 | 用户体验 | 可接受（延迟优先 > 音色）；edge 恢复后回主 |
| 帧长损坏导致客户端巨额分配 | ESP32 崩溃 | 服务端最大帧长守卫（8MB） |
| 流式帧传输中断 | ESP32 侧播放异常 | 测试覆盖弱信号场景（≥80% 成功率即可） |
| 长度前缀帧客户端解析 | ESP32 端需帧解析器 | v0.2 只交付 PC 端；ESP32 帧解析留 M1 |
| 真机 WAV 上传延迟大 | 端到端超 1.5s | M1 用 opus 线协议重新预算（A2 留白） |
