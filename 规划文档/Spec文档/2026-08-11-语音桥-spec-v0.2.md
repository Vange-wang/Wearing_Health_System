# 语音桥服务 Spec v0.2（2026-08-11）

> 本文档为 voice-bridge v0.2 的开发规格。继承 v0.1 全部架构约束，新增流式能力。
> 冲突时本 Spec 优先于 v0.1 Spec。WorkBuddy 按此实现。

## 1. 目标

在 v0.1 非流式基础上实现**流式语音交互**：DeepSeek 流式输出 + 分句 TTS 流水线，开口延迟 ≤ 1.5s（实测 1.2~1.4s）。同时覆盖 v0.1 CONDITIONAL_PASS 遗留的 4 条 Open Issues。

## 2. 阶段边界

| 阶段 | 内容 | 验收 |
|---|---|---|
| v0.1（已完成） | 独立语音服务：ASR + DeepSeek(非流式) + TTS | ✅ REVIEW_PASS |
| **v0.2（本文档）** | **DeepSeek 流式 + 分句 TTS 流水线 + VAD + health 增强** | **开口延迟 ≤1.5s，流式可感** |
| v0.3 | 接入 Hermes 会话（共用记忆/技能） | 与微信共用记忆 |

**禁止**：v0.2 不得接入 Hermes、不得更改 ASR 引擎（sherpa-onnx 锁定）、不得引入未列明的新增依赖。

## 5. 接口定义

### 5.1 GET /api/v1/health（v0.2 改造 — OI-001）

返回示例：
```json
{
  "status": "ok",
  "asr": "ready",
  "tts": "piper",
  "tts_fallback": "edge_unavailable",
  "vad": "enabled"
}
```

规则：
- `tts`：当前实际可用引擎（piper / edge），非仅主引擎名。
- `tts_fallback`：可选。仅当主引擎不可用时显示（如 `"edge_unavailable"`）。
- `vad`：`"enabled"` | `"disabled"`（取决于 config.yaml）。
- 启动时探测 edge-tts 连通性（发一个最小静音合成请求，超时 3s），不可用时记 `edge_unavailable`，health 始终反映真实状态。

### 5.2 POST /api/v1/voice/chat（v0.1 行为保留，不变）

非流式，完全向后兼容。v0.1 代码不改。WorkBuddy 不用动。

### 5.3 POST /api/v1/voice/chat/stream（v0.2 新增）

- 请求：同 v0.1 —— `multipart/form-data`，`audio` = WAV（16kHz/16bit/mono，≤15s）
- 响应：`Transfer-Encoding: chunked`，`Content-Type: audio/wav`
  - 每 chunk = **一句完整的 WAV 文件**（含 WAV header，16kHz/16bit/mono）
  - 客户端逐 chunk 播放：收到第 1 个 chunk → 开始播放（开口延迟计时止于此）
- 响应头：
  - `X-Timing-First-Token: {"asr_ms":..., "llm_ttft_ms":..., "tts_first_ms":..., "open_ms":...}`
    （`open_ms` = 从请求到第一个 chunk 首字节的开口延迟，核心验收指标）
- 错误：同 v0.1 错误码表（§5.4），流式错误时 HTTP 状态码在第一个 chunk 前发出

流式处理流程（详见 §6）：

```
WAV 上传 → VAD 预检 → ASR → LLM 流(chunk) → 句子缓冲器 → 触发条件满足 → TTS → chunked WAV 发送
                                                                                    ↓
                                                                        ESP32-S3 逐句播放
```

### 5.4 错误码表（v0.1 继承，v0.2 追加）

| 场景 | 状态码 | 响应 | 备注 |
|---|---|---|---|
| VAD 检测到静音/无效语音 | 400 | `{"error": "no_speech"}` | v0.2 新增（OI-007） |
| ASR 失败 / 无有效语音 | 400 | `{"error": "no_speech"}` | 继承 v0.1 |
| 音频格式不合规 | 400 | `{"error": "bad_audio_format"}` | 继承 v0.1 |
| 音频超过上限 | 413 | `{"error": "audio_too_long"}` | 继承 v0.1（上限 15s） |
| API key 未配置 | 500 | `{"error": "config_error", "detail": "..."}` | 继承 v0.1 |
| 服务未就绪 | 503 | `{"error": "service_unavailable"}` | 继承 v0.1 |
| LLM/TTS 上游失败 | 502 | `{"error": "upstream_error", "detail": "..."}` | 继承 v0.1；流式下首句前失败按此返回 |

## 6. 流式流水线设计（核心）

### 6.1 组件职责

| 组件 | 文件 | 职责 |
|---|---|---|
| `VADGate` | `app/vad.py` | 能量 RMS 阈值检测，决定是否继续走 ASR（≤rms_threshold → no_speech） |
| `SherpaOnnxASR` | `app/asr.py`（不改） | WAV → 文本（已有） |
| `DeepSeekLLM.stream_chat()` | `app/llm.py`（新增） | 用户文本 → 流式 `Iterator[str]` |
| `SentenceBuffer` | `app/splitter.py`（新增） | 接收字符流，按标点/长度触发分句 |
| `TTSEngine` | `app/tts.py`（改造） | 文本 → WAV bytes（piper 为主，同步合成） |
| `StreamingPipeline` | `app/pipeline.py`（新增） | 串联以上组件，产出 `Iterator[bytes]`（chunk WAV） |

### 6.2 分句规则（SentenceBuffer）

```
触发条件（任一满足即输出当前 buffered 文本为一句）：
1. 遇到标点：。！？〜 ；\n（中日英共用标点）
2. 缓冲区长度 ≥ 50 字符（长句保护，避免 LLM 不发标点时永不输出）
3. LLM 流结束：flush 剩余内容（即使无标点）

连续标点合并：多个连续标点仅算一次分割。
空句子跳过：纯标点/空白不触发 TTS。
```

### 6.3 TTS 策略（v0.2 — OI-004 评估结论）

edge-tts 6.x 现网持续 403（微软封老 client token），v0.2 的策略：

| 引擎 | 角色 | 延迟 | 质量 | 策略 |
|---|---|---|---|---|
| piper | **v0.2 默认主引擎** | 0.1~0.2s | 一般 | 本地推理，流程内同步调用 |
| edge-tts 7.x | 实验性（可选） | 0.3~0.6s | 自然 | 7.x 仅出 24k mp3，转码需引入 pydub（`pydub>=0.25`）；**config 中标记 `experimental`，默认关闭**。若用户主动开启且可用，TTS 走 asyncio 不阻塞 |

config.yaml 对应段：
```yaml
tts:
  primary: piper                                # v0.2 默认主引擎
  piper_model: models/piper/zh_CN-huayan-medium.onnx
  piper_config: models/piper/zh_CN-huayan-medium.onnx.json
  edge:
    enabled: false                              # 实验性，默认关闭
    voice: zh-CN-XiaoxiaoNeural
    version: 7
```

- edge `enabled: true` + `version: 7` → 需额外安装 `pydub`（requirements.txt 中注释说明）
- edge 不可用不影响服务：piper 始终可用

### 6.4 VAD 能量门限（OI-007）

```yaml
vad:
  enabled: true
  rms_threshold: 0.005    # 0~1，建议值 0.005；纯静音 rms ≈ 0.001~0.003
  min_speech_frames: 10    # 连续 speech 帧数下限（frame = 10ms），低于此 → no_speech
```

实现：
- 读取 WAV float32 samples → 分帧（10ms/frame，160 samples @ 16kHz）→ 每帧 RMS
- 连续 speech frame 数 ≥ `min_speech_frames` → 走 ASR；否则 → 400 `no_speech`
- 零新增依赖：numpy 已在 sherpa-onnx 依赖链中

### 6.5 流式打点（v0.2 追加时序点）

```
timing = {
  "asr_ms": ...,        # ASR 耗时（同 v0.1）
  "llm_ttft_ms": ...,   # LLM Time-To-First-Token（首 chunk 到达延迟）
  "llm_total_ms": ...,  # LLM 全流完成耗时
  "tts_first_ms": ...,  # 第一句 TTS 耗时
  "tts_total_ms": ...,  # 全部 TTS 总耗时（含所有句子）
  "open_ms": ...,       # 开口延迟 = asr + llm_ttft + tts_first
  "total_ms": ...,      # 全链路总耗时
  "sentence_count": ...,# 分句数量
  "chunk_count": ...,   # 发送 chunk 数
}
```

- `open_ms` 是核心验收指标
- 结构化日志打完整 timing
- 响应头 `X-Timing-First-Token` 包含首 token 相关字段

## 9. 验收标准（v0.2 全过才算完成）

### 9.1 功能验收

1. `POST /api/v1/voice/chat/stream` 返回 chunked WAV，每 chunk 可独立播放
2. 开口延迟 ≤1.5s（实测三句平均 `open_ms` ≤ 1500ms），目标 1.2~1.4s
3. 流式可感：第一个 chunk 和最后一个 chunk 到达时间差 ≥ 1s（证明不是等完整回复）
4. health 返回实际引擎状态（piper/edge）+ VAD 状态
5. 静音/VAD 拦截：纯静音 WAV → 400 `no_speech`（不走到 LLM，节省 token）
6. backtrack compat：`POST /api/v1/voice/chat`（v0.1 路径）行为不变

## 10. 延迟预算（v0.2 目标）

```
VAD        0.02s  （能量计算，numpy 向量化）
ASR        0.25s  （SenseVoice，不变）
LLM TTFT   0.50s  （DeepSeek 首 token，目标值）
TTS first  0.15s  （piper 首句，短句 5~15 字）
─────────────────
open_ms ≈  0.92s  （理论最佳）
实测目标    1.2~1.4s（含网络抖动+分句等待）
```

与 v0.1 计算公式对比：v0.1 等待完整 LLM 回复（2~3s），v0.2 只等首 token + 首句，开口延迟从 2-4s 缩短至 ~1.2s。

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| DeepSeek 首 token 延迟波动（0.4~1.5s） | 开口延迟超标 | v0.2 只要求平均 ≤1.5s；峰值超标不计入 fail |
| 分句等不到标点（LLM 长句无句号） | 首句永远不发 | 长句保护 50 字符硬切割 |
| piper 音色不如 edge 自然 | 用户体验 | 可接受（延迟优先 > 音色）；edge 7.x 实验通路保留 |
| edge-tts 持续 403 | 见 OI-004 | v0.2 默认 piper，edge 标记实验性 |
| 流式 chunk 传输中断 | ESP32 侧播放异常 | 测试覆盖 WiFi 弱信号场景（≥80% 成功率即可） |
| Chunked WAV 客户端解析 | ESP32 端需流式 WAV 解析器 | v0.2 只交付 PC 端；ESP32 端留到 M1 阶段适配 |
