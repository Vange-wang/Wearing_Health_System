- **分析方**：zcode（开发员）· 2026-08-19
- **对象**：`协同工作文档/2026-08-19-项目迁移-zcode执行任务单_hm.md`
- **任务**：`D:\workbuddy_project\项目\可穿戴健康辅助系统` → `D:\zcode_project\可穿戴健康辅助系统`，修路径引用
- **方法**：迁移前实地核查（venv 版本/运行中进程/自启脚本/路径引用规模/Hermes 侧）
- **结论先行**：**风险中等、可控，不是「风险太大」级别；但有 2 个必须正视的隐患（venv 版本漂移、会话工作目录失效），按规避方案可安全执行。**

## 一、风险逐项评估（实测证据）

| 风险项 | 等级 | 证据 / 分析 |
|---|---|---|
| **移动文件夹本身** | 🟢 低 | 源/目标同盘 D:，`mv` 只改目录项不搬数据（models 几 GB 也瞬时）；git 历史/remote/venv/models 整体走，`.git` 不依赖绝对路径 |
| **venv 断裂 + 重建回归** | 🟡 **中** | 见 §二，是本任务最大技术风险 |
| **运行中进程占用** | 🟢 低 | 实测 4 个进程占旧路径：6856(venv mdns)、8564(venv run.py)、14152(系统 mdns)、**7804(系统 run.py，监听 8710)**。迁移前停净即可 |
| **路径引用遗漏** | 🟢 低 | 项目内 `workbuddy_project` 引用仅 **8 个文件**，且多为叙述性（交接/会话存档/历史审查报告），功能性引用少 |
| **自启 bat** | 🟢 低 | 已读内容：`cd /d "D:\workbuddy_project\..."` 一处需改（GBK 编码） |
| **会话工作目录失效** | 🟡 **中** | 见 §三，执行环境隐患 |
| **Hermes 侧** | 🟢 低 | `~/.hermes` 下引用均为 `.hermes_history`/`.tmp`/日志/`hermes-cwd-*.txt` 缓存，非功能性配置；cwd 缓存会随下次启动自动刷新 |

## 二、最大技术风险：venv 重建会导致版本漂移

实测 venv 当前实际版本 vs requirements.txt 约束：

| 包 | requirements 约束 | venv 实际 | 漂移? |
|---|---|---|---|
| sherpa-onnx | `>=1.10.30` | **1.13.5** | 是（API 与模型兼容的基准） |
| numpy | `>=1.24` | **2.4.6** | 是（2.x 曾致 onnxruntime 崩溃，前科） |
| fastapi | `>=0.110` | 0.141.1 | 是 |
| edge-tts | `==7.2.8` | 7.2.8 | 否（已锁） |

**关键**：任务单 B2 建议「删除重建 venv + `pip install -r requirements.txt`」，但 requirements 是**宽松版本约束**，重建会装到**比现在更新的版本**（sherpa-onnx 可能 >1.13.5、numpy 继续 2.x），**破坏当前「能跑」的版本组合**——尤其 sherpa-onnx 与 `models/` 下模型的兼容性、numpy 2.x 的历史崩溃前科。

**规避方案（若执行，必须这样做）**：
1. **先不重建**：移动后直接测 `venv\Scripts\python.exe -c "import app"`。Windows venv 的 `python.exe` 通过 `pyvenv.cfg` 定位基础 Python（基础 Python 不在项目路径内，移动后不变），**大概率仍可运行**；断裂的是 `Scripts\pip.exe` 等 launcher 的 shebang，改用 `python -m pip` 即可绕过。
2. 实测 `python.exe` 能跑 → **保留 venv 不重建**（零回归风险）。
3. 若确实要重建 → 必须**先 `pip freeze` 锁当前版本**（`sherpa-onnx==1.13.5`、`numpy==2.4.6` 等），按 freeze 结果装，**禁止直接装 requirements.txt**。

## 三、执行环境隐患：当前会话工作目录会失效

当前 ZCode 会话的 primary working directory 就是**被迁移的目录本身**（`D:\workbuddy_project\项目\可穿戴健康辅助系统`）。迁移后此路径不存在，会导致：
- 后续工具调用的 cwd 失效（Bash 继承的环境 cwd 指向已删除路径）；
- 需要在迁移后立即 `cd` 到新路径重建上下文，否则后续任务可能报错。

这不是迁移失败，但会**中断当前会话的工作连续性**，需在迁移后第一时间切换。

## 四、综合结论与建议

**风险等级：中等，可控，非「风险太大」级别。**

但有一个更根本的权衡需要 Vange 确认：**迁移的实质收益只是目录名从 `workbuddy_project` → `zcode_project`（角色归属的象征），成本是服务中断 + venv 风险 + 会话 cwd 中断。** 如果只是要"项目归 zcode 名下"的语义，可以考虑：

| 方案 | 成本 | 说明 |
|---|---|---|
| **A. 按任务单迁移** | 停服务 + venv 处理 + 修 bat/引用 + cwd 切换 | 完整搬迁，一次性到位 |
| B. 暂缓，仅改远程仓库名/加说明 | 零 | 若迁移动机只是归属标识，其实项目归属由 git 远程（`Vange-wang/Wearing_Health_System`）决定，与本地目录名无关 |

**我的建议**：若 Vange 确认迁移有实质必要（如目录规范、多项目隔离），则**方案 A 可安全执行**——但必须遵守 §二规避方案（先测 venv 不重建、重建则锁版本），且我会在迁移后立即切换工作目录。若迁移仅是归属标识，建议**方案 B 暂缓**，避免无收益的动迁风险。
