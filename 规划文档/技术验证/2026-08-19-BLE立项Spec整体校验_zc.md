## 二、材料级缺口（SERIOUS，开工前必须补 Spec）

### 缺口1 · 预警① BOX-3 播报的下行通道未定义（最大缺口）

Spec §5.1 说**阈值级判定在 voice-bridge 做**，但 §2 架构图把「预警① BOX-3 本地语音播报」画在 BOX-3 自身分支下——**判定在服务端、播报在设备端，中间没有通道**：

- 当前固件（`voice_agent.c`）是纯客户端发起（按键 → HTTP 请求 → 收帧播放），**没有服务端→设备的推送通道**；
- 即使判定挪到 BOX-3 本地做，BOX-3 自己没有 TTS（语音都要服务端合成），本地播报仍需回服务端拿音频。

**需在 Spec 补决策**（二选一或组合）：
- A. **BOX-3 空闲轮询**：新增 `GET /api/v1/health/alert`，BOX-3 每 30~60s 轮询，有预警时服务端直接返回 WAV 帧播放（复用现有帧协议，固件改动小，预警延迟=轮询间隔）；
- B. **阈值判定下沉固件**：BOX-3 本地判阈值，触发时主动发一次「预警播报请求」到服务端取音频（无轮询，但阈值逻辑在固件、与 P4 服务端阈值重复维护）。
- 建议 A（阈值单点在服务端、可配，固件只加轮询）。

### 缺口2 · P3 语音查询会被 RAG 知识库截胡（实测实锤）

实测（2026-08-19，当前代码）：

```
「我的心率多少」→ RAG 命中 1 条：心率正常范围（knowledge/心率.md）
「我现在心率是多少」→ RAG 命中：心率正常范围
「血氧饱和度正常吗」→ RAG 命中：血氧正常范围
```

即：**P3 上线后，真实数据查询会先被 RAG 路由拿走**，轻量通道拿到的是静态科普文档（「正常心率 60-100」），而非用户实测数据——答非所问。

**需在 Spec 补路由规则**：新增 DATA 路由（真实数据查询关键词命中 → 优先级高于 RAG），且：
- **回答方式需定**：建议**模板直答 + TTS**（「您当前心率 78，属于正常范围」），不经 LLM——数据类回答要确定性，LLM 有读错数/编数风险，且模板直答首字更快；若走 LLM 则必须数据注入提示词（二选一，建议前者）；
- **同步改 SYSTEM_PROMPT 第 5 条**（`llm.py:49`「尚未接入」兜底要改为条件化，否则无数据时话术与有数据时矛盾）。

### 缺口3 · 微信通道配额与冷却策略不闭环

- 防误报设计：连续 3 次触发 + 冷却 **10 分钟**；
- iLink 配额：**24h/10 条**；
- 最坏情况：持续超标 → 6 条/小时 → **1.7 小时耗尽全天配额**，后续真实恶化预警反而发不出（只剩 BOX-3 本地 + 补报）。

**需在 Spec 补**：微信通道独立日上限（如 ≤5 条/天）+ 超限后的升级策略（连续恶化时缩短冷却但仍计日限 / 或超限后只走 BOX-3+电脑端，次日汇总补报）。

## 三、实施风险提示（NON_SERIOUS，开发时决策即可）

1. **心率 <50 夜间误报**：老年人睡眠心率 45~55 常见（窦性心动过缓），固定 <50 阈值夜间必误报。建议：夜间时段（如 23:00-6:00）阈值下调至 <45 或 <40，或夜间只对「持续 <45 且伴随血氧异常」报警。P4 调参项，先写进 Spec 阈值表备注。
2. **BLE 字节级协议未定义**：预研 D3 只有草案（8 字节帧：BPM+SpO2+时间戳+序号）。P1 开工前需固化为接口文档（UUID、字段、字节序、采样周期），P1/P2 两端共用的契约。
3. **固件代码未入库**：`voice_agent.c` 在 `D:\esp-box` 不在 git 仓库（多 WiFi 收尾时已发现）。P2 要大改固件，**建议先补一次固件入库**（或至少归档到项目仓库 `Code文档/固件/`），否则审查与回溯断层。
4. **数据新鲜度无验收线**：「最新值缓存」未定义过期语义（多久没更新算「数据中断」）。建议：>5 分钟无新数据，语音查询回答「检测暂时中断」；>30 分钟，预警功能自禁用（防陈旧数据误警）。
