## 一、问题定位（已确认，非实现缺陷）

| | v0.2 直连 DeepSeek | v0.3 走 Hermes agent |
|---|---|---|
| 首 token | 0.5~0.75s | ~3.1s |
| open_ms | 1.5s | 3.5s |

差值 ~2.4s = Hermes agent 启动开销（记忆检索 + skills 扫描 + 工具集解析注入 system prompt，模型处理大 prompt）。**非工具调用导致**（`tool_seen=false`），A2 分段计量 / A4 工具裁剪均无法消解。

**核心洞察**：3.5s 不是「接 Hermes」的必然，而是「每轮跑完整 agent」的代价。解法 = **解耦「记忆」与「完整 agent」**——记忆只读共享（快），agent 只在需要技能/工具时才跑（慢但值得）。

## 二、先讲清一个技术硬约束（为什么不能「先吐字再加载」）

记忆、技能清单、工具 schema 都是「提示词」的一部分。模型必须先读完整个提示词（含上述全部），才能吐第一个字。所以时序固定为：

```
加载(2.4s) → 首字(0.7s) → 流式
```

「加载」是「首字」的前提，顺序不可颠倒。因此缩短首字空窗只能走两条路：

- **瘦身**：提示词变小（裁技能清单、压记忆、工具按需加载）→ 首字提前。
- **预热**：agent 常驻/复用，加载动作发生在用户说话前 → 加载开销摊销。

两条都依赖 Hermes 侧能力，**需查证**（见 §四）。

## 三、三层解法

### 短期（v0.3 收尾，voice-bridge 侧可做，不动 Hermes）

**安抚语机制**：慢路径先发安抚帧。

- voice-bridge 检测到慢路径（Hermes SSE 出现工具指示 / 记忆检索迹象）时，先 TTS 一句安抚语（如「好的，我查一下」）作为**第一帧**发出去，用户立刻有反馈，再等正式答案。
- 快路径（纯闲聊）直接答，慢路径先安抚。
- 验收线放宽：纯闲聊稳态 open_ms ≤4000ms（含 agent 固定开销），冷启动剔除。

**效果**：不降低实际延迟，但消除「开口沉默」的焦虑，体验从「卡死」变「有回应」。

### 中期（单独立项查证，Hermes 侧能力）

**轻量直通 / 只注入记忆**：

- 纯闲聊走「bare 模型 + 只注入 memory，不加载 skills/工具」→ 延迟回 ~1.5s。
- 需要技能/工具时再走完整 agent（先安抚后慢答）。
- 关键查证点：Hermes 是否支持「只注入记忆、跳过技能/工具预加载」的轻量模式（或可通过 profile 级 skills 全关 + 工具最小集近似实现）。

**效果**：纯闲聊延迟回 ~1.5s，仅复杂请求付 agent 成本。

### 长期（知识库，voice-bridge 内置 RAG）

**知识库放 voice-bridge 层，不塞进 Hermes skill**：

- voice-bridge 自己维护知识库（向量索引 + 检索），用户问题 → 本地检索 → 检索结果 + 问题发给裸模型生成。
- 延迟 ≈ 裸模型 ~1.5s，不受 Hermes agent 拖累。
- 记忆仍共享 Hermes 那份（只读注入）。
- 关键点：知识库若做成 Hermes skill，则走完整 agent，延迟回到 3.5s+——**不推荐**。

**效果**：知识库问答快，且与「共用记忆」解耦（知识库 = voice-bridge 资产，记忆 = Hermes 资产）。

## 四、请求路由设计（目标态）

```
用户语音 → ASR → 路由判定
              ├── 纯闲聊/简单问答 ──→ 轻量通道（bare 模型 + 只注入记忆）──→ ~1.5s 开口
              ├── 知识库查询 ──→ voice-bridge RAG 检索 + 裸模型 ──→ ~1.5s 开口
              └── 需技能/工具 ──→ 完整 Hermes agent（先安抚「我查一下」）──→ 3.5s+ 开口
```

路由判定规则（WorkBuddy 实现，初期可保守：默认轻量，命中技能/工具关键词才走完整 agent）。
