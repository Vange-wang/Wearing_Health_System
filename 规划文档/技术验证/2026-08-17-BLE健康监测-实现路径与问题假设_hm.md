# BLE 健康监测 实现路径与问题假设清单（预研）

- **起草**：Hermes（deepseek-v4-pro）· 2026-08-17
- **背景**：毕设核心「健康数据监测」——BLE 腕部采集节点 + BOX-3 作 BLE central + Hermes 分析
- **性质**：提前布局预研，列出所有问题假设 + 解决方法，供 WorkBuddy/zcode 实施参考
- **依据**：毕设起草书（BLE 分布式传感网络）+ 乐鑫 BLE 文档 + MAX30102 资料实测调研

---

## 一、架构回顾

```
腕部采集节点(BOX 之外)                    AI 终端
ESP32-C3 + MAX30102(心率/血氧) ──BLE──→ BOX-3(ESP32-S3, BLE central, BLE 5.0)
  电池供电，BLE peripheral                  │ WiFi（与语音链路共用）
                                           └──→ PC(Hermes 智能体 → DeepSeek)
```

---

## 二、实现路径（分阶段）

| 阶段 | 内容 | 产出 |
|---|---|---|
| P1 | 腕部节点固件：MAX30102 采集 + BLE peripheral 广播/连接 | 心率/血氧能通过 BLE 发出 |
| P2 | BOX-3 加 BLE central：扫描连接腕部节点，接收数据 | BOX-3 能拿到心率/血氧 |
| P3 | 数据流打通：BOX-3 → WiFi → PC 数据接口 → Hermes 健康查询 | 语音问"心率多少"→ 真实数据 |
| P4（扩展） | ECG 胸部节点、多节点汇聚、运动状态 | 多源数据 |

## 三、问题假设清单 + 解决方法

### A. 硬件 / 传感器层

| # | 问题假设 | 解决方法 |
|---|---|---|
| A1 | MAX30102 对静电/过热敏感，焊接易损坏 | 用成品模块（免焊接，排针插接）；或烙铁接地 + 控温 |
| A2 | 腕部佩戴测量信号弱（MAX30102 设计为指尖/耳垂） | 首期**指尖式验证**（数据准），腕部作为形态目标；腕部需加大 LED 电流 + 算法调优 |
| A3 | 佩戴松动 → 运动伪影噪声 | 腕带固定；首期**静坐测量**，运动时数据标注"可能不准" |
| A4 | MAX30102 供电：1.8V 芯片 + 3.3V LED 双电源 | 成品模块自带稳压，单 3.3V 供电即可 |
| A5 | I2C 引脚冲突（ESP32-C3 的 SDA/SCL） | 查 ESP32-C3 引脚定义，选默认 I2C 引脚（如 GPIO8/9），避开 BOOT 等特殊引脚 |
| A6 | 模块上的 INT 引脚是否接（数据就绪中断） | 接 INT 到 GPIO（中断驱动采样，比轮询省电） |

### B. BLE 协议层

| # | 问题假设 | 解决方法 |
|---|---|---|
| B1 | GATT 服务设计：心率有标准服务，血氧无标准 | 心率用**标准服务 0x180D**（0x2A37 心率值，兼容性好）；血氧用**自定义服务**（自定义 UUID）或厂商特定；或两者合并一个自定义服务 |
| B2 | 默认 MTU 23 字节（20 字节 payload），传输低效 | NimBLE 自动协商大 MTU（247/512），一次可传心率+血氧多组 |
| B3 | 连接参数权衡（连接间隔：快/慢） | 持续传输用中等间隔（100~200ms）；省电用大间隔（500ms~1s）+ 从机延迟；Android 调试时 min interval ≥15ms（否则被断连） |
| B4 | BLE 栈选型：NimBLE vs Bluedroid | 选 **NimBLE**（轻量、内存小、性能好、ESP-IDF 推荐）；BOX-3 与腕部节点都用 NimBLE |
| B5 | BLE 5.0 vs 4.2 兼容 | BOX-3（ESP32-S3）BLE 5.0；腕部节点 ESP32-C3 也支持 BLE 5.0；两边都开 BLE 5.0 特性（长广播、大 PDU） |
| B6 | 广播 vs 连接模式 | 首期用**连接模式**（central/peripheral，持续传输可靠）；多节点后期可评估广播 + 扫描收集 |
| B7 | 配对/安全（健康数据隐私） | 首期 **Just Works 配对**（无密码，快速打通）；数据不上云（本地 PC），隐私风险可控；后期可加加密 |

### C. 功耗层（腕部节点电池供电）

| # | 问题假设 | 解决方法 |
|---|---|---|
| C1 | ESP32-C3 BLE 连接功耗 ~10-30mA，电池续航短 | 连接间隔拉大（1s）+ 从机延迟 4~8 → 平均功耗降到 ~几 mA |
| C2 | 实时持续传输 vs 周期采样 | **周期采样**（每 5s 采 10s 数据 → 发送 → 休眠），中间 light-sleep（保持 BLE 连接）或 deep-sleep（断开重连，更省电但复杂） |
| C3 | MAX30102 LED 功耗大 | 采样时才开 LED（占空比控制），空闲软件关断（零待机电流） |
| C4 | 电池选型 + 续航估算 | 200mAh 锂电：平均 5mA → 40h；平均 1mA → 200h。首期验证用 200mAh，够演示 |
| C5 | ULP 协处理器（深度睡眠监听） | 后期优化项：ULP 睡眠时监听传感器，超阈值唤醒主 CPU；首期不引入（复杂度高） |

### D. 数据 / 算法层

| # | 问题假设 | 解决方法 |
|---|---|---|
| D1 | 心率算法（PPG → BPM） | 用现成库（SparkFun MAX3010x 库 / Algo 库）或自己实现：带通滤波（0.5-4Hz）+ 峰值检测/FFT；实测校准 |
| D2 | 血氧算法（红/红外比值 → SpO2） | 现成库自带（查表校准）；实测对比指尖血氧仪校准 |
| D3 | 数据格式 | 心率 BPM（int）+ 血氧 %（int）+ 时间戳 + 序号，打包成固定长度 BLE 帧（如 8 字节/帧） |
| D4 | 数据准确性验证 | 与指尖血氧仪（几十元）对比，误差 ±3% 内可接受（健康辅助定位，非医疗） |

### E. 集成层（BOX-3 + Hermes）

| # | 问题假设 | 解决方法 |
|---|---|---|
| E1 | BOX-3 BLE + WiFi 共存（语音链路用 WiFi） | ESP32-S3 双模支持 BLE+WiFi 分时共存；BLE central 任务与语音任务分优先级（语音优先，BLE 数据后台收） |
| E2 | BOX-3 FreeRTOS 任务分配 | 新增 BLE central 任务（低优先级，数据缓存到队列/PSRAM）+ 现有语音任务（高优先级）；确认内存（BOX-3 有 8MB PSRAM，够） |
| E3 | 数据到 Hermes 的接口 | BOX-3 收到心率 → WiFi POST 到 PC 语音桥新端点（如 `/api/v1/health/data`）→ Hermes 健康查询路由读最新数据 |
| E4 | 语音查询集成 | 路由加「健康数据查询」：用户问"心率多少"→ 命中 → 读最新心率 → 真实数据回答（替代"即将上线"）；健康数据由腕部节点提供，实时数据不编造 |
| E5 | 健康建议（创新点） | Hermes 结合心率数据 + 用户描述 → 人设化健康建议（"心率 98 偏快，注意休息哦～"）；用轻量通道（快）+ 数据注入提示词 |

### F. 可靠性层

| # | 问题假设 | 解决方法 |
|---|---|---|
| F1 | 首次配对流程 | 腕部节点开机广播 → BOX-3 按键触发扫描/连接 → 连接成功存地址（NVS 保存对端 MAC，下次直连） |
| F2 | 断线重连 | BLE 断开事件 → 重连逻辑（周期扫描指定 MAC → 重连）；腕部节点掉电/出范围 → BOX-3 后台自动重连，不阻塞语音 |
| F3 | 数据掉包 | BLE 连接事件自带重传机制（链路层）；应用层加序号校验，缺失帧标记（"数据中断"提示） |
| F4 | 多节点扩展（未来） | NimBLE 支持多连接（资源有限）；或广播模式 + 扫描收集；胸部 ECG 节点复用同一框架 |

## 四、关键决策点（待 Vange/实施时拍板）

1. **腕部节点硬件**：ESP32-C3 小板（便宜够用）vs ESP32-S3（更通用）？——建议 C3（BLE 传输够用，成本低）
2. **数据模式**：周期采样（省电）vs 持续传输（实时）？——建议周期采样（每 5s 一组，续航优先）
3. **GATT 服务**：标准心率服务 + 自定义血氧服务（首期）
4. **指尖 vs 腕部**：首期指尖式验证（数据准），腕部是形态目标

---

## 五、实施风险排序（先做难/关键项）

1. **A2（腕部信号弱）**——最可能翻车的点：MAX30102 腕部测量信号弱 + 运动伪影。首期用指尖式规避，腕部作为二期优化。
2. **D1/D2（心率/血氧算法）**——数据准不准决定毕设可信度，先用现成库，实测校准。
3. **E3/E4（数据到 Hermes 集成）**——语音查询闭环是毕设成果 3 的核心。
4. **C（功耗）**——续航是"可穿戴"的体验指标，周期采样即可达标，不阻塞。
