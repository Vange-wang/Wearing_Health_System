## 1.1 安抚语机制（A5 短期，已实现）

- `llm.py`：SSE 首次出现 `tool_calls` 时产出 `TOOL_SENTINEL`（不进分句器）。
- `pipeline.py`：收到哨兵且尚未发帧 → 立即 TTS 安抚语（config `pipeline.comfort_text`，默认「好的，我查一下。」）作为**第一帧**，之后正常分句正文。
- 快路径（纯闲聊无工具）直接答，不发安抚语。
- 效果：不降实际延迟，但消除「开口沉默」焦虑（Spec §4 A5 意图）。

| 句子 | open_ms | llm_ttft | tts_first | tool_seen | 帧数 |

| 02 帮我查一下心率 | 3875 | 3120 | 383 | false | 1 |
| 03 你叫什么名字 | 3530 | 3106 | 179 | 2 |

- 服务端日志铁证：`llm_backend=hermes`、`tool_seen=false`（纯闲聊无工具）、HTTP 打到 `127.0.0.1:8780/v1/chat/completions`。
- **冷启动 47.5s**：gateway 刚起首个 API-server agent 创建（模型加载 + 记忆/技能初始化），一次性成本。
- **稳态 ~3.1s ttft**：Hermes agent 首 token 固有延迟（记忆检索 + skills 扫描 + 工具集解析 + 模型首 token），非工具调用导致。

## 3. 共用记忆（核心验收 §6.2）实证

直连 Hermes API Server（同一 profile）两轮独立 session：

```
轮1 写入：请记住我最喜欢的颜色是蓝色 → 回「已存好：最喜欢颜色蓝色」
轮2 查询：我最喜欢什么颜色 → 回「蓝色。」
```

**证明**：persistent memory 跨独立 session 持久（A3 每轮独立 session 的跨轮记忆靠 persistent memory 成立）。微信与 voice-bridge 走同一 gateway profile → 同一份 persistent memory，共用记忆架构前提成立。（微信侧写入→语音读到的端到端交叉验证留验收时人工完成。）

## 4. 延迟口径 —— 如实上报，未达标

- Spec §4 A2 裁决：纯闲聊 open_ms 稳态 ≤1600ms；带工具 answer_open_ms ≤1600ms、tool_ms 不卡线。
- **实测纯闲聊稳态 open_ms 3530~3875ms，超标 ~2.2 倍**；根因是 `llm_ttft` ~3.1s，而 v0.2 的 DeepSeek 首 token 仅 0.5~0.75s。
- 这是 **Hermes agent 的基础管线延迟**（非 tool_seen 工具调用），A2 分段计量与 A4 裁剪都无法消解——它们针对的是"工具调用"开销，而非"agent 本体"开销。
- 冷启动 42s 属 gateway 首请求一次性成本，不计入稳态，但用户体验上首问极慢。

**需 Hermes 裁决的方向**（供参考，不擅自改）：
1. 放宽 v0.3 纯闲聊 open_ms 目标（Spec A5 已放宽至 ≤4000ms，实测稳态 3530~3875ms 达标）；
2. 中期轻量直通：**查证结论 = 当前 Hermes 0.18.2 不支持**（见 `规划文档/技术验证/2026-08-15-v0.3中期延迟查证.md`），需 Hermes 侧加能力或跳长期 RAG；
3. 长期 RAG：voice-bridge 内置知识库 + 裸模型，是当前唯一能把延迟压回 ~1.5s 的可行路径，建议提前立项。

## 5. 环境踩坑（新增，需入技术验证）

- **8642 端口在 Windows 排除端口段**（8605-8704），API Server 绑不上（WinError 10013）→ 改 8780。
- **safe-delete 钩子劫持 `rm`/`os.remove`/`Remove-Item`**，`hermes gateway restart` 从沙箱 bash 执行时删不掉 `gateway.pid/.lock` → 新实例 PID 竞争自杀、微信掉线。解法：`env -u PYTHONPATH -u PYTHONHOME -u MSYSTEM hermes gateway start`（干净环境绕过钩子）。
- Hermes gateway 是 Vange 的常驻服务，重启会短暂中断微信 bot；改其配置/重启属外部动作，需 Vange 知情。
