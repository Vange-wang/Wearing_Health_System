## 2. 实测链路（固件串口证据）

```
btn PRESS_DOWN -> start recording      ← GPIO0 顶部圆键按下
btn PRESS_UP   -> stop recording       ← 松开
REC END, bytes=106496                  ← 录音 3.3 秒（106496B ÷ 32KB/s）
UPLOAD DONE, bytes=106496              ← 上传完整，零丢失
HTTP status=200                        ← 服务端成功响应
（随后收到长度前缀 WAV 帧并播放）
```

## 4. 排障记录（两个关键坑）

### 坑1 · 按键不触发
- **现象**：按顶部圆键无反应，串口无 `btn` 事件。
- **根因**：BOX-3 顶部圆键 = **GPIO0 = BSP_BUTTON_CONFIG**（非 GPIO1/MUTE）。之前受 chatgpt_demo 用 MUTE 做静音键误导绑错。
- **定位**：加 GPIO 电平诊断（`gpio_get_level` 直读，不依赖 iot_button 事件机制），按顶部圆键时 GPIO0 从 1→0 实锤。
- **修复**：MUTE + CONFIG 双注册。

### 坑2 · PCM 上传 400（协议层）
- **现象**：服务端 uvicorn 报 `Invalid HTTP request`，一个字节 PCM 都没收到。
- **根因**：`esp_http_client_open(client, write_len)` 中 `write_len >= 0` 走 **Content-Length**，只有 `write_len < 0` 才走 chunked。原代码 `open(client, 0)` 实际发 `Content-Length: 0` 却往 body 写数据 → 协议冲突。且 esp_http_client 的 chunked 请求上传**不做自动 chunk 编码**（write 是 raw write）。
- **修复**：改为**先录音到 PSRAM（512KB=16s）→ 松开后用 Content-Length 一次性上传**（`open(client, total)` + write）。LAN 下 opus 无收益、PCM 直传最可靠，服务端 `request.stream()` 兼容。

## 5. 延迟计量（真机实测，服务端落盘日志）

| 轮次 | 语音内容 | 路由 | open_ms | llm_ttft_ms | tts_first_ms | 判定 |

| 第1次 | 「你还在吗」 | lightweight | 4315 | 3126 | 1032 | 冷启动（DeepSeek 冷连接一次性） |
| 第2次 | 「你刚刚是不是卡住了」 | lightweight | **989** | 584 | 198 | ✅ 稳态达标（目标 ≤2000ms） |

- 流式 ASR partial 逐字更新正常（"你还在"→"你还在吗"→ final）。
- 路由正确：纯闲聊走 lightweight（DeepSeek 轻量通道），llm_backend=deepseek。
- 冷启动 open_ms 4315ms 为 DeepSeek 首次连接 + ttft 预热（一次性），稳态 989ms 达标。
